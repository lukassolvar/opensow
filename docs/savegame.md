# Savegames

Code: `crates/opensow-formats/src/save.rs` (container, state stream walker and writer), `saveobj.rs` (object records, reader and writer), `savespark.rs` (`opensow save <file>`, `saverec`, `savestate`, `savelayout`). Read from the exe: save function `0x428bb0`, state serializer `0x42a400` (store and load in one function, MFC `Serialize` style), info writer/reader `0x42be20`, compressor `0x439240`, decompressor `0x439860` (class `CHuffcomp`, the only use found). The install's `Savegame` folder ships empty, so there are no sample files. Instead of samples the exe's **own store branch is run in an emulator** on random game states and compared with the Rust reader / writer ("Verification" below); the constants are also tested by `savegame_constants_match_the_exes_save_code`.

## Verification (what is exe-checked)
- `scripts/verify_save_layout.py` (disassembly scan): header magic and scalar order of all 11 classes.
- `scripts/verify_save_store.py` (emulator): for each of 14 record classes 60 random objects are built in emulated memory (vtables found in the image, pointers, lists, routes, children, bools with values other than 0/1) and the exe's `Serialize` store branch is run on an in-memory `CArchive`. `opensow saverec` parses the bytes, re-writes them and prints every field with its object offset; the script requires: every byte consumed, `write(parse(x)) == x`, and **every parsed `(path, offset)` equals the memory value at that offset** and nothing is missing. 840 objects, 0 mismatches. It found the bullet's third spark array (below).
- `scripts/verify_save_state.py` (emulator): the whole state store function `0x42a400` runs on 40 randomised game states (all globals it reads: head scalars, per-player words and byte arrays, list records, the map object with cell layers / cameras / items, PlayerState / Stock / Params blocks, speech queues with CStrings, the decal flag grid, unit / building / bullet / squad slot tables with objects, decal and cloud lists; the MFC `CString` / `CArchive` imports are small emulations). `opensow savestate` parses the stream, checks `State::to_bytes` reproduces it **byte for byte** and prints a summary that the script compares with memory (head, player words and arrays, lists, map size / scroll / cameras / cells, slot counts and present slots, decal flag grid orientation, counts, speech texts). 40 states, 0 mismatches. It found the 4-byte header of the campaign record (below).
- Unit tests: every class round-trips through `Object::write` / `parse` (`every_class_round_trips_through_write_and_parse`), the state writer is the byte-exact inverse of the walker (`walks_a_synthetic_state`), the Huffman encoder's tree equals a literal port of the exe's scan (`huffman_tree_matches_a_literal_port_of_the_exes_scan`).
- `scripts/verify_save_load.py` (emulator, **the load direction**): the exe's load branch of `0x42a400` runs on the streams `World::to_state` wrote for M01, M05, M10, M16 and M22 and for four synthetic worlds (corpses, beam shots, blinks, a Rogon blast, clouds, orders, a firing top; `OPENSOW_DUMP_STATES=dir cargo test -p opensow-game savestate`) (900 ticks in, with air strikes and up to 26 bullets in flight), then its store branch runs on the objects it built, and the result must equal the input byte for byte (except the 317-byte campaign record, whose filler the exe re-randomises). So the exe's own code accepts our streams: every record header and section tag is checked by it, its constructors build the objects, its `Serialize` methods read every field, the post-load grid rebuilds run, and nothing is lost on the way. Negative controls: a flipped record magic and a damaged tag are rejected. Stubbed because they need files, MFC or the level: the level loader `0x4267d0` (it only records the level number), operator new / delete, `CString` / `CArray` / `CArchive::Read` helpers, the string reader `0x404440`, the campaign file access `0x456770` / `0x456720` / `0x456e50`, the cloud trim `0x453060`, the CRT's `memcpy` / `memset` (their implementation switch reads CPU feature words the emulation never sets). Streams of the exe's own store branch from *random* states do not load: their random unit positions index outside the grids (`0x45a4df`), which the real game never produces.
- Not emulated: the container steps of `0x428bb0` (temp file, compressor, `.info`); the compressor was read and matches `huff_encode` (tree: merge two smallest weights, ties by node index, left = smallest; tree written root first as `byte, left, right`; codes MSB first in `u32` words, a partial last word flushed; `0x439240`, `0x439cf0`, `0x438e60`).

## Corrections found by the emulation
- **Bullet**: the three spark arrays are *triples* `(+0xc+4i, +0x48+4i, +0x84+4i)`, 15 of them (earlier notes: 15 pairs).
- **Campaign record `0x456ac0`**: it is a full record, so it starts with the 4-byte header (`u16 1, u16 0x1d6c`) before the 313 bytes (`SIGNATURE_LEN` = 317). `config::PassedLevels::parse/write` already did this for `player.cfg`.
- **Decal flag grid** (`0x513878`, 128x128): stream index `y*128 + x` holds memory byte `x*128 + y` (outer loop over the low index, `0x42aa70`), the same orientation as the map cells. Values are written as `byte == 1`.
- **Bool fields** are stored as `byte == 1` (0/1 whatever the memory byte holds).
- `0x456770` (called right before `0x456ac0`) reloads the campaign object from `player.cfg` (a `CFile`); the save then serialises the reloaded object.

## Files
`Savegame\savegame_<stem>.data` and `.info` (the stem of slot 0..9 is built by `0x41f060`, docs/saveload.md). Saving first writes the state to the temp file `savegame\t`, compresses it into `.data`, deletes the temp file, then writes `.info`; afterwards it plays `01-game-saved.wav`. It needs 2 MB of free space ("Error: you need more that 2MB free space"). Everything is little-endian MFC `CArchive` data (no alignment).

## `.info` (the load menu's entry)
`u16 2, u16 0x1e5`, `u32` checksum of the `.data` file (`[this+0x94]`, the byte sum `0x436ba0`; docs/saveload.md), four MFC strings (title `[+0x84]`, `%X` time, `%b %d, %Y` date, `%a %H:%M`), `u32 [0x517aec]`, then a 160x120 RGB565 screenshot (the u16 range `0x71065c..0x719c5c` of the exe's memory). MFC string = `u8 len` (or `0xff, u16`, or `0xff, 0xffff, u32`) + ANSI bytes.

## `.data` (compressed state)
Huffman with the exe's own layout: `u32` uncompressed length, `u16` root index, nodes from the root down to 0 (`u8` symbol, `u16` left, `u16` right; a leaf has both `0xffff`), then the codes as `u32` words read from bit 31 down (0 = left, 1 = right). Decoding stops after `length` bytes. `save::huff_decode`; `huff_encode` produces valid but not byte-identical streams (the exe's tie-breaking is not reproduced).

## Decompressed state stream (`0x42a400`)
`u16 1, u16 0x5a10`, then in order (load reads the same order and checks the tags):
1. scalars: `u32 [0x49a33c]` (level: the loader calls `0x4267d0` with it first, so the map and objects come from the level, then the saved state overwrites them), `u32 [0x71c0f4]` (lockstep RNG index, `rng.rs`), `u32 [0x5baafc]` (1 after the new-game reset, otherwise unread: meaning unknown), `u8 [0x49a339]` (mission-start flag), `u32` x4 `[0x5baad8]` (black radar toggle) `[0x5baadc]` (radar tick accumulator) `[0x5baac4] [0x5baac8]` (countdown minutes, seconds), `u8 [0x5baa99]`, `u32 [0x89cf50]` (`save::StateHead`).
2. three players (index i): `u32 [0x517af8+4i]`, `u32 [0x517b04+4i]`, `u32 [0x5baaa0+4i]`, then byte arrays of 1000 (`0x5bb910`), 300 (`0x5bc4c8`), 500 (`0x5bc850`) and 30 (`0x5bce30`) bytes per player.
3. three records of two counted lists of `u32` (`0x6bf90c/0x6bf910` and `0x6bf948/0x6bf94c`, stride 0x14).
4. object serializers (decoded below, "Global serializers"): `0x459960` on `0x6bf980`; `0x455700` x3 (stride `0xc68` from `0x70ba50`, the players' state); `0x419100` x3 (`0x338`, `0x6bed08`); `0x465220` x3 (`0x80`, `0x6bf788`); `0x456ac0` on `0x71c38c`. Then tag `"P2v3"` (MFC string).
5. `0x403b20` on the speech objects `0x6bf6b0 + 0x20*i` (i up to `[0x575720]` inclusive), tag `"aS2n"`.
6. the decal flag grid `0x513878` as 128x128 bytes (stream index `y*128+x` = memory `x*128+y`, written as `byte == 1`), then the units: for each of 3 players a `u32` count (`0x575734+4p`) and 1000 slots (`0x5b62c0 + 0xfa0*p`), each slot a byte 0/1 followed, when 1, by the object's own `Serialize` (vtable +8). Tag `"Ua63"` (the exe's error text calls this "unit loading").
7. buildings the same way: counts `0x575740+4p`, 300 slots at `0x5bab00 + 0x4b0*p`; tag `"B17u"` ("building loading").
8. 500-slot objects (counts `0x57574c+4p`, `0x5b91a0 + 0x7d0*p`, probably bullets) and 30-slot objects (counts `0x575758+4p`, `0x5ba910 + 0x78*p`), same format, no tag.
9. two counted object lists: `[0x49a3d8]` items from `[0x49a3d4]`, `[0x49a400]` items from `[0x49a3fc]`, each item `Serialize`d; tag `"Checksum"` (checked on load; nothing follows it), then `0x437d10` runs.

After the tag `"Checksum"` the loader (`0x42bbf3..0x42bc52`) sets `[0x6bfa34]` = 2 (full redraw), runs the seven grid rebuilders (`0x458230`, `0x4582a0`, `0x458420`, `0x458360`, `0x458190`, `0x4580d0`, `0x458010`: terrain plus the live units/buildings stamped back into the pathfinder's grids, docs/pathfinding.md), then trims the cloud list to the options (`0x453060`, docs/clouds.md), then `0x437d10` refills the visual random table with the C runtime's `rand()` (not saved). So all post-load fixups are known; they derive from the saved objects, none carries state of its own.

A mismatching tag shows "The savegame is corrupted" (with "(panel2 loading)" for `P2v3`, "(asituation loading)" for `aS2n`, "(unit loading)", "(building loading)").

## Field meanings (`Class::field_name`, `NAMES=1 opensow savelayout`)
The scalar fields whose meaning is established by the rest of the project (each name comes from a constructor or update function that is documented elsewhere) are named in `saveobj.rs`; the test `named_fields_are_serialized_fields` checks that every named offset really is a serialized scalar. Unit: `+0x14/+0x18` pixel position, `+0x2c` dead, `+0x30/+0x34/+0x38` maximum hit points / hit points / death threshold, `+0x3c` handle, `+0x40` kind, `+0x44` player, `+0x4b` flyer, `+0x4c` anti-air, `+0x5c/+0x60` hit flash, `+0x7c` target handle, `+0x84/+0x88` hover phase / offset, `+0x8c` idle look-around, `+0x90/+0x94/+0x98` corpse timer / variant / flag (docs/effects.md). Top: facing count, sprite index, flash set, aim offset (`+0x5c/+0x60`), fire phase, facing and turn counters, target handle, reload. Chassis: kind, team, speed, sprite sheet, facing / target facing, turn and animation counters, goal pixel `+0x5c/+0x60`, step cell `+0x6c/+0x70`, re-search cooldown, order words. Order: valid, type, x, y, two words. Building: cell, size, flags `+0x68/+0x69`, hit points, owner, kind, linked Advancer, destruction state, headquarters / satellite fields, spawn cell and exits, slot count, active slots, upgrade points, AI threat; BuildingPart: kind, target, progress, rate, ready, unlock price, value. Bullet: flight progress, path length, trail counters, facing, type, class, strength, speed, owner, animation fields, the two variants (docs/effects.md), target handle. Aircraft: position, target, height, handle, speed, code, hit points, direction, death and explosion timers. **Named: all 271 serialised scalars** (`NAMES=1 opensow savelayout`; unit 28/34, top 14/24, chassis 35/42, order 6/6, weapon 10/16, building 56/65, building part 7/9, bullet 18/24, aircraft 17/34, decal 4/4, cloud 3/3, player state 1/3, stock 2/4, speech 2/2, map item 1/1). Added in the last pass, with their sources: unit box `+0x1c..+0x28` (-16, -16, 32, 30 in the unit initialiser `0x46bd30`), `+0x38` (death threshold *and* health-bar divisor: `0x46e040` kills at `hp <= it`, `0x46a420` draws `max / it` pixels), `+0x50` view-ring radius, `+0x64` bar offset, `+0x68` turret building handle, `+0x80` kept anti-air target; chassis Advancer action `+0xf4/+0xf8/+0xfc/+0x100` (docs/advancer-actions.md says `[top+..]`, but these are the chassis' offsets), `+0x150` idle counter, `+0x64/+0x68` current cell, `+0x74/+0x78` second step cell; weapon (embedded at top `+8` and chassis `+0x104`) `+4` enabled, `+0x10/+0x14` range, `+0x18` spread, `+0x20` reload, `+0x24` jitter, `+0x2c` bullet type, `+0x30` strength, `+0x40` state (aim.rs and docs/advancer-actions.md use the top-relative offsets, which are these plus 8); building footprint end, sprite hotspot, animation states and frame bounds, blink fields, destruction animation counters, rally point, preview flag. **Last six** (from the code): chassis `+0x14` is a copy of the unit handle (third argument of the initialiser `0x46ff50`), `+0x7c` a byte that says the step cell `+0x6c/+0x70` is reserved in the unit grid (`0x46f550`); building `+0x5c` switches a second sprite layer in the draw `0x4092f0` (the constructor sets it only for kind 104), `+0x2bc` an additive overlay effect that `0x4096e0` draws at the pairs `+0x26c/+0x294`, `+0x50` a sub-counter (-1 at construction, 0 after a state change); aircraft `+0x20` is the **side** (it indexes the statistics block, `0x467b0c`). Fields marked \"unused\" are only touched by the serializer and the constructors. Not every name is a full explanation (the sprite-layer and overlay flags are described by what the drawing code does with them).

**Constructor values** (`scripts/gen_building_defaults.py`): the exe's building constructor `0x40a330` run in the emulator for kinds 25-29 and 100-108 gives the full set of values a new building holds (layout mask `+0x98..`, hotspot, animation bounds and period, exits, the eight turret spots `+0x224..`, `+0x120`, health bar scale, ...). The table is `sim/building_defaults.rs`; `World::to_state` starts every building record from it and overwrites what the sim knows (cell, hit points, owner, tallies, slots, ...), and sets the animation state `+0x48` (3 working, 4 damaged at hp <= max/2, 5 destroyed, 6 neutral). The unit test `the_constructor_table_agrees_with_the_decoded_building_tables` checks the emulated table against the hand-decoded `formats::buildings` tables (footprint, hotspot, bounds, period, layout masks): two independent readings of the same constructor agree. Writing the layout mask matters: the exe's load restamps the map layers from it, and `verify_save_load.py` found that the `no_build` layer must be set under every blocked footprint cell (`0x40ad69`) for the stream to come back unchanged. 

**Unit, top and chassis values** (`scripts/gen_unit_defaults.py`, table `sim/unit_defaults.rs`): the same approach for the unit initialiser `0x46bd30` (stdcall(x, y, player, kind, slot, handle); it builds the Top with `0x4796f0` + `0x479eb0` and the Chassis with `0x46e250` + `0x46ff50`, the base weapon init is `0x47c630`), run for kinds 1-15, 40-46 and the turret guns 109-113 (kind 46 has no top, the guns no chassis). The unit record, the top (including its 10 + 80 word arrays `+0x94` / `+0xcc` and the embedded weapon: range, spread, reload, bullet type, ...), the chassis (facing count, speed, sprite sheet, draw offsets, animation period, ...), its current order and the Advancer's beam weapon all come from that table; `World::new_unit` builds them and the sim's own state (position, hit points, facings, counters, orders, route, beam timer) overwrites the sim-known fields. Two things in the records depend on the player (the table is the same for 0, 1 and 2 except for these): the top weapon's `+0xc` and the chassis' `+0x10` (the sheet team: `0x46e8f0` takes the blue sprite array when it is 0, else the green one) hold the player number. The **sprite size words** (top `+0x64/+0x68`, chassis `+0x20/+0x24`) are the one part that comes from the install: they are the 16-bit header words `+8` / `+0xa` of **frame 0** of the sheet's `_blue` sprite file (`sprite::Frame::extra[0..2]`, the pointer arrays `0x575770` tops / `0x593b30` chassis that `0x423d80` fills), as `(word + 1)` sign-extended from 16 bits for the top and one more for the chassis (a missing sheet gives 0 and 1). The generator runs the initialiser twice with different fake frame headers to separate those four fields from the rest and asserts the formula (including the wrap at `0xffff`); `formats::units::SheetSizes` implements it and `Art::sheet_sizes` reads the words from `sprites.data` without decoding pixels (`World::sheet_sizes`, filled by `Play::new`; without an install they are 0 / 1, which is what the exe holds for a missing sheet). The test `the_unit_initialiser_table_agrees_with_the_decoded_tables` compares the table with the hand-decoded constants (`fill_unit`, `units.rs` sheet names, `anim::walk_params` facing counts and speeds).

**The pixel line is the chassis' local route** (`0x46ee80`): the Bresenham line from the unit's pixel to the step cell centre is built into the `CArray` at chassis `+0x98` (data `+0x9c`, count `+0xa0`; the stream writes the count and the pairs), start point included, and the walking step `0x46f550` pops the first pair into the unit's position for every pixel step. So mid-segment the list holds the points still to walk (nearest first), and right after the segment was planned it still starts with the unit's own pixel. The sim now keeps exactly that list (`Line { goal, rest }`, replacing the incremental error term; `the_stored_pixel_line_is_the_incremental_bresenham` shows both walk the same pixels on 2000 random segments) and `World::local_route` / `unit_from_record` map it to the record and back (`a_walking_units_pixel_line_is_the_local_route`: stream, reload, identical continuation; `scripts/verify_save_load.py` runs such a stream through the exe).

**Slot `+0x1c` is the unlock price** (500 / 200, set by the slot setters `0x40e730`, `0x40e8f0`), `+0x20` the tech levels bought; the sim's `waiting` counter has no stream field. Constructor values of the still unnamed building fields (`0x40a330`): `+0x50` -1, `+0x13c` 1, `+0x398` 0, `+0x2bc` 0 (set to 1 by `0x408d60`).

**Writers.** `Object::write` (any record), `MapState::to_bytes` (incl. map items), `State::to_bytes` (the whole stream), `SaveInfo::to_bytes`, `StateHead::to_bytes` and `huff_encode` (byte-identical to the exe's compressor) are exe-verified as described under "Verification". What is *not* done is the **bridge between OpenSOW's simulation and these records**: the original loads a stream by overwriting live objects field by field, so a stream we write must give every serialised scalar a value the exe accepts, and the sim has to be rebuilt from the loaded fields. OpenSOW therefore still saves its own snapshot (docs/saveload.md); the design for the bridge is in "Next: the sim bridge" at the end of this file.

## Global serializers (step 4 and 5, `save::State`)
`save::State::parse(data, speech_objects)` walks a whole decompressed stream (synthetic-tested; there is no real save to try). `speech_objects` is `[0x575720] + 1`, a run-time global that is not saved (the exe sets it to 0 or 1).
- **Map object** (`0x459960`, class size `0x4c0cc`, `MapState`, no header words; the **same stream is the `.map` level file**, so `MapState::parse` reads every shipped map and `to_bytes` reproduces it byte for byte, `map_files_are_map_object_streams_that_round_trip`): MFC string = the version tag `VER7` (the CString `0x71cec8`; the loader shows "Wrong map version!!!" when it differs; earlier notes called it the level path); `u32 [+0x20]`, `[+0x2c]` = player 0's scroll position in pixels (the other players' are cleared on load; the level file's `a`, `b`); width `[+0x40]`, height `[+0x44]`; for each of height x width cells (outer loop over the height counter y, inner x, memory index `x*128+y`) 17 bytes, see below; `u8` marker + (marker 1 only) `u32 3` and three **camera records**; `u32` n and n MapItem records (`+0xbc` array, count `+0xc0`). The load code only tests the marker for 1: a level file has 0 and then n = 0 (the five bytes after the cells). MapItem (`0x43e480`, magic `0xab30`): `u32 +0xc` kind; kind 0: `u32 +4,+8,+0x10,+0x14,+0x18` and bools `+0x1c,+0x1d` (x, y = the sort key of `0x458ce0`, `+0x18` the building handle `0x457ef0`/`0x4597e0` look it up by; the static building sprites `0x4586a0` draws); kind 1: `u32 +4,+8,+0x10`; other kinds nothing.
  - **Cell layers** (all indexed `x*128+y`; read from the readers/writers of the absolute addresses `0x6bf980 + offset`, and checked on the 24 shipped maps): `u16 coord [+0xcc]` = `(x<<8)|y` (never read); `u32 ground [+0x80cc]` = the walkers' obstacle grid: `0xFFFFFD` terrain, a building's handle while it stands (stamped by `0x40ad3c`, cleared by `0x40b0d5`), copied into the wave/unit grids by `0x458230`, `0x4582a0`, `0x458360`, `0x458420` (docs/pathfinding.md; an earlier version of this note said `+0x170cc`); `u32 air [+0x180cc]` = the air layer's terrain (outer ring, no-fly areas), copied by `0x458190`, `0x4580d0`, `0x458010`; `u8 [+0x280cc]` = always 0 (the only writer, `0x436130`, ANDs it with a ring mask); `u8 no_marks [+0x2c0cc]` = no scorch decal, flying piece or smoke puff may land here (read by the impact code `0x410459`, `0x4106ce`, `0x40fc18`, `0x40fe26` and the unit unload of an aircraft squad, which also needs a free unit-grid cell, `0x468b8d`; only M02 sets it, 497 cells); `u8 no_build [+0x300cc]` = buildings and turrets may not be placed (the placement test `0x408cfc` refuses it; a footprint sets it at `0x40ad69`, destruction clears it); `u32 building [+0x340cc]` = the covering building's handle (footprint stamp `0x40ad5b..`, picking `0x417899`/`0x418da9`/`0x41f6dd`, the damage lookup `0x42f3fd` and the "within 2 cells of an own building" placement test).
  - **Camera record** k (player `k`, `CameraState`): `bool +4+k` a smooth scroll-to is active, `u32 +8+4k`, `+0x14+4k` its target (top-left pixel, clamped; set by `0x4588c0(x, y, k)`, followed by `0x458bb0`), `u32 +0x54+4k` shake ticks left, `+0x48+4k` shake step divider, `+0x60+4k`, `+0x6c+4k` shake epicentre (`0x458620`, docs/options.md "QUAKE"); the shake's step list (`+0x7c+0x14k`) is not saved and is cleared on load. The player's current scroll is `+0x20+4k`, `+0x2c+4k` (`0x457f80(dx, dy, k)` moves it by twice the delta).
  - **After the stream** the load branch rebuilds every derived grid itself (inline in `0x459960`, the same code as the callable `0x458010..0x458420`): it re-stamps each building (`0x40e460`) and copies `ground`/`air` into the seven working grids `0x5eac38..0x64ac38` (docs/pathfinding.md) with each unit's cell or handle on top, then `0x42bbf8` sets the redraw flag `[0x6bfa34]` = 2.
- **PlayerState** (`0x455700`, `0x70ba50`, stride `0xc68`, magic `0x41c2` v2): `u32 +0x38,+0x3c,+0x40`, then 10 `u32` from `+0x10`.
- **Stock** (`0x419100`, `0x6bed08`, stride `0x338`, `0x7b33`; vtable `0x487904`; docs/hotkeys.md calls it the "pointer object"): it is the **player's input / HUD state**, not a stock. The key flags (`+0x64 + scan code`) and mouse flags are *not* saved; what is saved: `u32 +0x2dc` (Tab round-robin index, `select_next_unit`), `+0x32c`, `+0x330` (both -1 initially, not traced), `+0x2e0` (H round-robin index over Advancers), the **nine numpad camera bookmarks** as pairs `(+0x2e4+8k, +0x2e8+8k)` (pixel x, y; initial values `0x1c0,0x640 / 0x400,0x640 / 0x6c0,0x640 / 0x1c0,0x440 / ...` from the constructors `0x414a70`, `0x414d50`, `0x415020`; Shift+numpad k sets bookmark k, numpad k jumps), then ten `CArray` objects (`+0x214 + 0x14k`, vtable, data pointer `+4`, count `+8`; the save writes the count and the `u32` items; purpose not traced, the key handler `0x415ba0` does not use them).
- **Params** (`0x465220`, `0x6bf788`, stride `0x80`, `0x18c7`): 30 `u32` from `+4`, `u32 +0x7c`.
- **Signature = campaign progress** (`0x456ac0`, the `CPassedLevels` object `0x71c38c`, magic `0x1d6c`): written after the three Params as the 4-byte record header plus 313 obfuscated bytes carrying the 50 level states (317 bytes); decoded by `config::PassedLevels` (docs/config.md).
- **Speech queue** (`0x403b20`, `0x6bf6b0 + 0x20*i`, `0xf8a8`): `u32 +4,+8`, count `+0x14`, then SpeechItem records (`0xd8db`: MFC string, `u32 +8,+0xc,+0x10,+0x14`).
- Remaining sections as listed above; the decal flags are 128x128 bytes, the slot groups `u32` count + presence byte and record per slot (1000 units, 300 buildings, 500 bullets, 30 squads per player), then decal and cloud lists.

## What OpenSOW saves (the bridge, `sim/savestate.rs`)
A save file is the original's state stream (`World::to_state`, below) **followed by an OpenSOW extension** after the `Checksum` tag: MFC strings `OpenSOW4` and the level name, a `u8` campaign (1 = Warmonger, docs/warmonger.md), a `u32` length and OpenSOW's own snapshot (three `f32` camera values and `World::snapshot`, serde JSON). The exe's loader never reads past the tag, so the exe-layout part stays a valid savegame, while OpenSOW restores from the extension and continues **exactly** (everything the stream cannot carry is in it). A file without the extension (a save of the original) restores through `World::apply_state` instead; saves of older OpenSOW builds (`OpenSOW1`-`3`) are no longer read. The container is as before (`.data` Huffman, `.info`, docs/saveload.md). Payload between `Play::snapshot` and the store: `u32 n`, the `n` stream bytes, our snapshot (`saveui::pack_payload`). Test `a_saved_game_continues_exactly_where_it_was_saved` (restored game runs 600 ticks identical to the unsaved one) still holds.

**Handles** (found in the exe's allocator `0x43a9b0`, args `(class, type, player, slot)`): `handle = slot | generation << 10 | player << 16 | type << 19 | class << 22`; class 1 unit, 2 building, 3 bullet, 4 aircraft squad; type is 0 for everything but units, which get 5 (anti-air walkers 1, 2, 3, 42), 4 (Advancer), 3 (turret guns 109, 111, 112, 113), 6 (anti-air gun 110) or 1 (jump table `0x46c1b4`, `unit_handle_type`). `generation` is the slot's counter byte **before** the increment; **the four per-player byte arrays of the stream (1000 / 300 / 500 / 30 bytes) are exactly these counters** (0..60, wrapping at 61: `0x43a9e5`), indexed by slot. The bridge hands out slot = order of creation per player and generation 0 (counter 1).

**`World::to_state(level, progress, scroll)`** writes: head (level number, RNG index, carryall counter `v_89cf50`), the player words (credits, research, windtrap level sum), the per-slot counters, the map object (cell layers from the sim's grids: `ground` = terrain `0xFFFFFD` or the covering building's handle, `air`, no-marks, no-build, `building`; camera records with the quake), PlayerState (strike lock), input records (default bookmarks), Params (the statistics counters `[side*0x80 + 4 + 4k]`), the campaign record, the speech object's last event position, the decal flag grid and decals, **buildings** (cell, footprint, hit points, tallies, owner, kind, Advancer handle, destruction animation, satellite fields, production slots as the five parts, upgrade points, rally point), and **units** (position, hit points, kind, player, handle, selection flag, chase target, hover phase, look timer; Top: facing, target facing, turn counter, aim target, reload; Chassis: facing, target facing, turn and animation counters, phase, cell, destination, step cell, cooldown, idle counter, current order, route; every living turret gets its gun unit 109..113 with `[unit+0x68]` = the building handle).
**`World::apply_state`** is the reverse on a freshly built world of the same level (like the exe: level first): scalars, buildings matched by cell and kind (the slot tables follow the stream; a level structure missing from the stream is destroyed), units replaced (their ids become their handles), turret guns folded back into the structures' aim and target, decals.
Test `a_mission_round_trips_through_the_original_state_stream` (missions M01, M05, M10, M16, M22 after 900 ticks, with a bomber and a tripler launched; up to 26 bullets and 2 aircraft in flight): the stream parses and re-writes, applying it to a fresh world gives the same units, structures and credits, writing the restored world gives a **byte-identical** stream, the world keeps running, and the same works through the save container as a file without the extension.

**Bullets and aircraft** (second slice): a `Bullet` record holds `2*index` / `2*points` coordinate words, the lift array at `+0xc4` and **only the points still to fly** (`+0xd44 + 8k` x, `+4` y for `k >= index`; on load earlier points repeat the first saved one), type, strength, speed, owner, trail, facing, the four animation words `+0x2670..+0x267c`, variant and the target handle (unit or class-4 aircraft handle); an `Aircraft` record holds position, target, altitude, aim offset, handle (class 4), speed, force code, hit points, direction, death and cloud timers, the animation words, exhaust and glow frames, counter / state, bomb travel, spawn offsets, armed flag and squad index (a load builds the squad with `Aircraft::launch` and overwrites these; the private exhaust / glow countdowns and sound flags restart). The kept anti-air target of units and turret guns is `[unit+0x80]` = the aircraft handle (`World::air_targets`).

**Third slice (sim-only state that has a stream field).** Clouds (`Cloud` records x, y, speed; the exe re-rolls the picture on load and trims the list to the options); the computer's strategy and timer are **PlayerState `+0x38` and `+0x3c`** of the enemy block (`[0x70ba88]`, `[0x70ba8c]`, now named); the mission countdown is the head's `[0x5baac4]` minutes and `[0x5baac8]` seconds (docs/ai.md); the Advancer's action is chassis `+0xf4/+0xf8` (cell centre pixel), `+0xfc` (1 destroy, 2 repair, 3 upgrade) and `+0x100` (building handle) and its beam timer the weapon record at chassis `+0x104` (`+4` enabled, `+0x1c` counter, `+0x20` reload, `+0x40` state); a type-2 straight flight is the current order (type 2) with the cell it leads to as the first entry of the order list, and the rally order the next entry. The campaign record in the stream is the game's real progress (`Play::progress`). Test `orders_beam_ai_timer_and_clouds_survive_the_stream` (a synthetic world) and the mission round trip.

**Fourth slice.** The Advancers' beam shots are the exe's bullets of type 19 (repair), 20 (upgrade) and 21 (destroy): strength is what one landing does (repair `2 * rate`, otherwise `rate`), `+0x2688` is the building handle, `+0x268c` the number of sparks and the three arrays `+0xc`, `+0x48`, `+0x84` their offset x, y and frame; they share the bullet slot table. A destroyed unit's slot keeps a unit record with the dead flag `+0x2c` and the corpse timer / variant / blasts-thrown flag `+0x90..+0x98` (the sim's corpses). A building that blinks after being given as a target has `+0x14c = 1` with timer `+0x150`, state `+0x154` and toggles left `+0x158`; a turret gun's look-around timer is its `+0x8c`.

**Fifth slice.** The Rogon blast is a bullet of type 35 (`0x411dc0(0x23, 0, x, y, x+20, y+20, owner)`): start and end coordinates in `+0x269c/+0x26a0/+0x26a4/+0x26a8`, the state machine in `+0x26c4` (counter, starts at 20) and `+0x26c8` (step k). A turret or unit **top** keeps its state and cooldown counter in the embedded **weapon** record (`+0x40` state 0 / 3 / 4 / 6, `+0x1c` counter: base class `0x47c5f0`, aim.rs), its target search counter in `+0x80`, the fire-sequence tick in `+0x20c` and facing / target facing / turn counter in `+0x6c/+0x70/+0x74`; the earlier bridge wrote the cooldown into `+0x210`, which is the step length (corrected). The carryall's exhaust and glow countdowns are `+0x58` / `+0x68` (frame counts 4 and 2, reloads 2 and 4 are constants).

**Not saved by the exe either** (checked: no field of the stream, the globals `[0x71c0e8]` hint phase and `[0x70f2c8]` AI air-strike timer lie outside the saved ranges, so the exe restarts them on load too): the mission-1/6 hint phase, the AI's air-strike timer, wrecks and effect sprites. **Not carried by the stream bridge** (a genuine save of the original, or a stream loaded without our extension, restarts these): wrecks, explosion and smoke sprites (the exe's `AnimSprite` lists are not saved either, so this matches it). Two more sim states have no stream field **by the original's design**, so they live only in our extension and a stream-only load restarts them like the exe does: (1) the **tutorial script**: its step `[0x70f2cc]` is not in any saved range (the state function `0x42a400` never reads it; the pause menu hides Save and Load in the tutorial, but the F5 handler `0x416811` does not test it), so after a load of level 0 the step is -1, i.e. a plain mission with the HQ rules and the computer opponent; `Play::restore` does exactly that for a stream without our extension (`the_tutorial_script_is_only_in_our_extension`); (2) the **visual random generator** (`0x437cd0`: table `[0x71c0f8]` of `[0x71c100]/2 - 10` words, cursor `[0x71c0fc]`): neither is in the stream, and `0x437d10` refills the table from the C runtime's `rand()` and resets the cursor after every load, so even the original does not continue its visual randomness (hover phase starts, smoke jitter, sparks); our extension keeps ours for an exact continuation. The unit's Bresenham line is **not** in this list any more: it is the chassis' local route in the stream (above). The generation counters are 0 or 1, so handles of destroyed-and-reused slots do not occur. (The view zoom has no field in the exe; it lives in our extension.)
