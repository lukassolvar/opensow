# Ground-unit walking

Code: `formats::wave` (`Wave::find`, `Wave::local_step`), `formats::walk::pixel_line`; used by `World::find_path_on` / `World::avoid` in `opensow-game/src/sim/movement.rs`. The three routines are verified against the exe in the emulator (`scripts/verify_against_exe.py` sections 8-10: wave pathfinder, pixel line, local avoidance; 300 random cases each, 0 mismatches).

## The chain (chassis step `0x46f550`, per walking step)

Unit object `[unit+0x14/+0x18]` = the unit's pixel position, chassis `[+0x5c/+0x60]` = its destination pixel (set by orders; "arrived" is position == destination). A unit takes `steps_at(speed, tick % 60)` single-pixel steps per tick (docs/art.md); each step:

1. **Arrived** (position == destination): pop the next order from the order list `[chassis+0xc8]` (stride 0x1c) and set up its goal (`0x470480`).
2. **No pixel route** (`[+0xa0] == 0`): count `[+0x80]` down; below zero it is reset to 6 and the global route is searched with the wave `0x4753a0` (start = destination, target = the unit, so the route comes back unit first; docs/pathfinding.md). A failed search clears the orders (the unit stays). Whether or not a search ran, `0x473190` then plans the next cell.
3. **`0x473190(x, y)`** (single player; networked games use the two-step planner `0x472f50`, docs/pathfinding.md, "The second-step search") (the unit's position): clears the unit's old cell in its occupancy grid, runs the local search `0x476870` (below), and if that fails tries `0x4774c0` (the reachable cell nearest to the destination, scanning the ring list `0x65bbd8` that `0x436230` builds, `rings.rs`; docs/pathfinding.md, "The fallback `0x4774c0`") and finally sets the destination to the unit's own position; stamps the unit's handle on the new step cell `[+0x6c/+0x70]`; removes the first cell of the global route; builds the pixel line to the step cell centre with `0x46ee80`.
4. **Each step**: the unit's facing must be within 4 turn steps of the wanted one (`0x46a190`), then the position becomes the next point of the pixel line (one pixel per step) and the line shrinks; when the line is empty step 2 repeats.

Units whose type byte `[type+0x4b]` is nonzero - only the **Advancer**, kind 40 - use the air set of grids (`0x60ac38`, `0x62ac38`, searches `0x474b30` / `0x473f10`): the same code on grids with the map's border layer as terrain, so Advancers fly over lakes, mountains and buildings and only avoid the map edge, no-fly areas (a few maps) and each other (docs/pathfinding.md, "The air layer"). The game does the same: `World::find_path_on(true, ..)`, `Occupancy.air`/`air_stat`, `World::is_air_blocked`. An Advancer given a move order (type 1, UI right-click) follows a wave route like any unit; the factory exit walk (`0x408890`, order type 2) is a straight line (`World::order_fly_straight`). The player's building orders (`0x46b8b0..0x46bbf7`) are type 1 too (`push 1` before `0x4706a0` at `0x46b9c6`), so they use the wave route and the local avoidance: an Advancer already hovering over the work cell blocks it and a second one stops beside it, out of beam range and with its order lapsed (original behaviour; test `a_second_advancer_stops_next_to_the_one_working_on_the_building`).

## `0x46ee80` pixel line

The line lives in the chassis' local route (`CArray` `[chassis+0x98]`, savegame stream; docs/savegame.md): `0x46f550` pops one point per pixel step, and `Unit.line` holds the same list (`Line { goal, rest }`, next point last). Integer Bresenham, start included: `d = 2*minor - major`; each step moves one pixel along the long axis, and along the short axis too when `d >= 0` (then `d += 2*(minor - major)`, else `d += 2*minor`); equal axes count as y-major. `walk::pixel_line`.

## `0x476870` local avoidance (mode 0)

Grids: unit grid `0x61ac38` (terrain `0xFFFFFD`, buildings, other units, each cell holds a handle; free is below the base `[0x49a36c]`), static grid `0x5eac38` (terrain and buildings only, base `[0x49a360]`). `route` is the global route (the unit's own cell first), `L = route[min(len-1, 6)]`.

- No route beyond the unit's cell, or `L` is the unit's cell: no step. `L` holds a building (static grid >= `0x1fffff` and not the unit's own handle): no step.
- `L` next to the unit: step there if it is free in both grids, else stop (the exe sets the destination to the unit's position); no local route is stored.
- Otherwise: the four diagonal corners of the unit's cell are closed (`0xFFFFFD`) where one handle fills both orthogonal cells on that side (unit grid value equals the static value of the other orthogonal cell and is occupied) - so a unit never cuts the corner of a building; then the same wave as `0x4753a0` runs from `L` to the unit's cell over the unit grid (the unit's cell and `L` are free); the route back from the unit's cell (same smallest-stamp walk, at most 1000 steps) gives the next cell and the local route. The corner cells and the cells around `L` are restored afterwards; the base moves past the stamps.
- A failed search gives no step; `0x473190` then tries `0x4774c0`.

**Differs from the exe:** OpenSOW's unit waits and retries on the next tick, after `World::retarget_to_free_cell` has moved its destination and searched the route at once (docs/pathfinding.md, "The fallback").

## In the game

`find_path_on` uses the exe's orientation. The unit keeps the exe's two-level structure (traced from `0x46f550`, `0x473190`):

- `Unit.path` is the **global route** `[chassis+0x88]`. It is searched from the destination `Unit.dest` (`[chassis+0x5c/0x60]`) when an order is given and then again every 7th planning round (`Unit.cool` = `[+0x80]`, reset to 6, searched below zero) or when detours have used it up while the unit is still away from its destination. Local avoidance never rewrites it: `0x473190` only removes its first cell per planned step. (An earlier port spliced the local detour into the route, which made units zig-zag and even turn back.) `path[0]` stands for the segment in flight and is dropped when the unit gets there.
- `Unit.step` is the **step cell** `[unit+0x6c/0x70]` (its centre pixel): the first cell of the local search `0x476870`, chosen when the pixel line is empty (`World::plan_step` -> `avoid`). The unit walks the Bresenham line to it; it may differ from `path[0]` when units are in the way.
- The walking step loops over the `steps_at(speed, tick % 60)` pixel steps of the tick, like the exe: each pass plans when the line is empty, recomputes the wanted facing from the pixel to the step cell centre (unless the unit stands on it), runs the chassis **turn counter** (`ChassisAnim::turn`), and moves one pixel only if the facing is within 4 turn steps (`within_turns`). The chassis tail (`tick`) turns once more, so a unit that takes a pixel step turns twice as fast as one standing still (`0x46f65f` and `0x46f8b9`).
- A new move order (`order_move`, e.g. the chase every 7 ticks) does **not** touch the pixel line: a unit mid-segment finishes the walk to its step cell and the new route is searched from that cell (`path[0]` = that cell's centre). Dropping the line made units restart from the middle of a segment, often towards the cell behind them.

Before a unit starts a path segment `avoid` runs the local search over the grids of the tick (`Occupancy`). Like the exe, the game rebuilds them once per tick before the turns (`0x42d775..0x42d7b1`: `0x458230` copies terrain and buildings, `0x4582a0` / `0x458190` stamp every unit's current cell into the static grids `0x5eac38` / `0x60ac38`, `0x458420` / `0x4580d0` its step cell into the unit grids `0x61ac38` / `0x62ac38`; a standing unit's step cell is its own cell, a dying one stamps `0xFFFFFD`) and then stamps them as things happen: a pixel step into another cell clears the old static cell and stamps the new one (`0x46f759` / `0x46f7ff`, `World::occupancy_moved`), `0x473190` clears the old step cell and stamps the step cell after the search, new or kept (`0x4731b6`, `0x47321c`), a new unit stamps its cell into the ground static grid (`0x46c0b9`, also for an Advancer), a corpse stamps `0xFFFFFD` every step (`0x46e004`) and clears its cell when its slot is freed (`0x46a230`). Units planning later in the same tick see all of it. Because the static grid holds the units, a unit standing on the look-ahead cell `L` stops the walker (`0x476989`: any object there, not only a building), corners are closed around standing units too, and other units block the chase's approach wave (`0x477630`); test `a_unit_standing_on_the_look_ahead_cell_holds_the_walker_back`. The Rogon bomb avoids like every other ground unit: the exe's movement code has no branch on kind 46 (docs/ai.md). The Advancer's type-2 flight (`order_fly_straight`) sets the step cell directly: a straight line, no planning.

**Differs from the exe:** a building placed or destroyed during a tick changes the grids only at the next tick's rebuild, as in the exe, but the port builds them on first use in the tick, so a building finished by the mission script before any search already counts in that tick. The stamping order within one rebuild is the unit list's, not the exe's slot order; it matters only where two units' cells coincide.

Known limit: the exe's global wave may cut a corner between two blocked cells (docs/pathfinding.md) which the local search then refuses; a unit in such a pocket can walk back and forth (random maps with isolated blocked cells; real maps keep the border blocked and rarely have this).

## Orders (`chassis+0xc4..0xcc`, `0x470480`, `0x4706a0`, `0x46e510`)

The chassis keeps a list of orders (`[+0xc8]` data, `[+0xcc]` count; each 0x1c bytes: vtable, valid byte `[+4]`, type `[+8]`, x `[+0xc]`, y `[+0x10]` in pixels, two more words). `0x4706a0(type, x, y, a, b)` replaces the whole list by one order and executes it (when the unit already stands on its destination it also stores `a`, `b` and the facing in `[+0x168..0x170]`); `0x46e510(type, x, y, a, b)` appends (the walker's teleport script uses it); `0x46f950` (arrival) pops the head and `0x470480` starts the next. An empty list gets a type-0 order (do nothing). `0x470480` executes the head:
- type 1: the destination `[+0x5c/+0x60]` becomes (x, y) if inside the map and the re-search cooldown `[+0x80]` is cleared (the next step plans a route);
- type 2: destination as above, the pixel route is dropped and replaced by a straight line from the unit to (x, y) (`0x46ee80`) with the step cell set to the destination cell - a move without path finding;
- type 3: destination only (when inside the map).
Callers of `0x4706a0`: the UI orders (`0x418a42`, `0x4190c8`), the mission scripts (`0x42e644`, `0x42e6db`), the walker teleport and the Advancer/air code.

## Chasing a target (`0x46eb40`, `0x477630`)

`[unit+0x7c]` is the handle of the unit's chase target (set by right-clicks on enemies; the AI order `0x469fe0(target, 0)` sets it only for one call of `0x46eb40` and then clears it, docs/ai.md). Whenever the unit would plan a route (idle, or at each re-search) `0x46eb40` checks the target: a dead or vanished target clears it (a building target is dropped when the unit is a kind-40 Advancer); the target cell is the unit's cell or the building's centre (`origin + size/2`). The weapon range `[chassis+0x154]` is `(min + max) / 2` of the weapon top (5 for anti-air tops, 1 without a weapon). If the cell distance (`0x437720`: truncated Euclidean) is at most `range - 1` nothing happens (the unit keeps its orders and walks on to the cell it was already sent to). **Nothing in the weapon code stops the chassis**: the unit loop (`0x46e114..0x46e243`) updates the top (`0x479c60`) and the chassis (`0x46f140`) every tick independently, and the only writers of the chassis order list are the order setter `0x4706a0` (UI, scripts, factory exits, Advancer) and this chase replan, so a unit shoots while it walks and stops only where its route ends (an earlier version of the port cleared the path as soon as the weapon had a target; test `units_keep_walking_while_they_shoot`). Otherwise `0x477630` computes where to stand: `wave::approach`, exact vs emulation (300 random grids, 235 destinations, 65 failures, same destination and same new base): a bucket wave from the unit (orthogonal step = one generation, diagonal = two) until it reaches a cell next to the target, then `range` steps back along the lowest stamps from the *target* cell. The result replaces the order list by one type-1 order for that cell's centre; if there is no way the destination is set to the unit's own position (stop). Building targets get their own cells freed in the 7 x 7 block around them (grid value equals the handle). The exe's distance is measured to the building's **middle** cell, so a range-1 unit (walker 45, `(0 + 1) / 2` = 0, raised to 1 at `0x46c0f9`) at a wall is never within range: as an idle unit it runs the chase every tick (`0x46f140` -> `0x46f4a0` -> `0x46eb40` at `0x46f537`), gets a new order into the building and steps its legs while it shoots.

**Differs from the exe:** a unit chasing a building stops re-ordering as soon as its weapon's scan (`Rings::target_search`) reaches one of the building's cells, so it stands still while it shoots (`World::chase_step`; test `a_range_one_walker_stands_still_and_shoots_buildings_and_turrets_from_every_side`).

Handle type 4 (an Advancer target) is the same search over the air grid (`0x478200`, `wave::approach_air`, with a block-clearing quirk; docs/pathfinding.md); the game uses it for targets of kind 40.

The game's `chase_step` does exactly this (a Rogon bomb uses the same chase with range 1 and explodes once the target is in the 3 x 3 block around it, docs/ai.md).

## Not decoded

**The orders' two extra words** (`0x4706a0(type, x, y, a, b)`, `0x46e510`, order constructor `0x478f50` stores them at `+0x14`, `+0x18`): callers that run for the local player pass `(a, b)` = a word plus the game clock `[0x70ef98]` (`0x418a42`, `0x4190c8`, the Advancer orders `0x46b9c8..0x46bc48`, the convoy scripts pass `0xb90`/`0xb0` as x/y); the factory exits and the chase (`0x46ed62`) pass `(0, 0)`. They are the start clock of the networked position calculation `0x46fa40` (docs/pathfinding.md); a unit already on its destination keeps them in `[+0x168..0x16c]` for the next replan `0x46f5d7`. Single player never reads them. The networked variant `0x46fa40` (position from the game clock, planner `0x472f50`, the second-step search `0x475c30` / `0x4732f0`) and the fallback `0x4774c0` are decoded and verified (docs/pathfinding.md); the game uses `0x4774c0` (`World::retarget_to_free_cell`).

**Differs from the exe:** having no network play, the game never runs `0x46fa40`, `0x472f50` or the second-step search; units reserve one cell ahead as in single player.
