# Effect sprites (bullets, explosions, smoke)

Code: `crates/opensow-formats/src/effects.rs`. Exe checks: `tests/real_data.rs` (`extras_table_matches_the_exes_loader`, `bullet_draw_table_matches_the_exes_draw_function`, `impact_sounds_match_the_exes_impact_function`, `animation_spawn_sites_match_the_exes_calls`). Viewer/game use: `blit_blend` in `opensow-viewer/src/render.rs`, `Play::draw_shots` in `opensow-game/src/play.rs`.

## The sprite table

`0x424700` (the start-up sprite loader) reads every effect sprite file with the same call shape: `push cap; push dest; push ecx; mov ecx, esp; push name; call 0x45dab0`. `dest` is a static array of frame pointers at a fixed address, `cap` the number of frames the loader will keep (the file's real frame count is smaller or equal; neighbouring arrays may overlap beyond it, e.g. `sizer` / `plasma`). `effects::EXTRAS` lists 82 entries (`extras\*`, `__extras\*`, `specials\*`; the file is `<name>.ps6` inside `sprites.data`). Code refers to a frame as `[array + 4*index]`, so an address inside an array names a frame (the shell sprites are `gula2` frames 1 and 2 at `0x5e6694` / `0x5e6698`; `effects::extra_at` resolves that).

Unit explosion pieces are not in this table: `Units\<name>_blueboom` / `_grenboom` (80 frames per unit, arrays `0x5870b0` / `0x58a2b0`, stride `0x50` per unit name in the `units::TOPS` order plus the 1AA..3S names) are loaded by the unit loader `0x4246xx`.

`extras\bigexplo\e_air2` and `e_bubg` have `_low` variants loaded into the same arrays when `[0x49a33a]` is **0** (`0x4250d7`: `cmp [0x49a33a], 0` / `je` takes the `_low` names); the creators then store draw mode 7 (`0x45e560` doubles the sprite's width and height) instead of 6 (`mode = 6 + ([0x49a33a] == 0)`, `0x409d03`, `0x4679a0`, `0x467acb`). So 1 = full detail (the game's choice), 0 = low detail. OpenSOW: always full detail (no `_low` sprites, mode 6).

## Bullets

Bullets are objects of size `0x26cc` (docs/projectiles.md). Drawing is `0x410a30` (jump table `0x410e7c`, one case per type); `0x414020` is the matching erase pass for the exe's dirty-rectangle renderer (same sprites, it also erases the previous position `[+0xc0]`, which is why the arcing types look like they are drawn twice there; the picture shows only the bullet at its lifted position, there is no separate shadow sprite).

`effects::bullet_draw(type)` gives the layers (sprite array, frame rule, blit routine), exe-tested for all 34 types:

| type | draws |
|---|---|
| 1 | `missile` frame = facing `[+0x2654]` (plain), then `MissileFlare` frame 0 (additive); the facing is `facing(start, end, 32)` of the path builder's arguments (`0x40efab`, `Path::facing`), fixed at launch, so frame = the 32-step facing exactly (emulation-verified) |
| 2, 3 | `gula2` frame 1 (plain); 4: `gula2` frame 2; 5: `gula2` frame 0 |
| 6-9, 12, 14, 20, 27, 31 | nothing |
| 10 | the satellite laser column at the *end* of its path, see below |
| 11 | `plasma` frame = counter (additive) |
| 13 | `wreck_bu1`/`wreck_bu2` frame `[+0x268c]*20 + counter` |
| 15, 16 | unit boom sprite `blueboom`/`grenboom` frame `[+0x2680]*80 + counter` (a destroyed unit's flying pieces): the file is `units\\{TOPS[variant]}_blueboom.ps6` / `_grenboom.ps6` (16 frames, plain blit); the game draws it at the bullet's position (`--fx CX,CY,piece,VARIANT` headless) |
| 17 | `tripler_ph` frame = progress (additive) |
| 18 | `bomba_l`/`bomba_r` frame `[+0x268c]*20 + progress` |
| 19, 21 | `bodky_b` / `bodky_r` fragments: `[+0x268c]` of them, each with its own offset and frame (additive) |
| 22 | `fighter_smoke` (the smoke blend) |
| 23 | `dim1..dim4` frame `[+0x2680]*21 + counter` |
| 24, 25 | `meteor_medium` / `meteor_small` (plain) plus their `_aura` (half blend) |
| 26 | `fighter_bomb` frame = counter |
| 28 | `elektron` frame counter + 1 (additive) |
| 29, 30, 33 | `heavylaser` frame 0 (additive) |
| 32 | `menu\001_lights` frame 0 (additive; a loose `Sprites2` file) |
| 34 | `walker_blast` frame 0 (additive) |

**Frame advance** (`0x411c8x`, once per logic step; `[0x552494]` steps per tick): types 17 and 18 take the frame from the flight progress `p = [+0x2644]` (twice the path index): `min((p-2)/20, 19)` and `min((p-2)/50, 8)`. All other types count `[+0x2678]` down; at zero it is reloaded from `[+0x267c]` and the counter `[+0x2670]` goes up by one (type 22, the fighter's smoke, adds one more when the counter is a multiple of 3); at `[+0x2674]` frames it wraps to 0, and types 22 and 23 end instead (the bullet is removed). The four values come from the constructor (`projectile::BULLET_TYPES.anim`). `effects::BulletAnim` implements this.

**Flamer beam** (bullet types 8 and 9 draw no sprite in `0x410a30`): the flight step `0x411220` (branch `0x4118e2`, `cmp edx, 8 / 9`) decrements `[+0x264c]` once per *path step*; at 0 it reloads `[+0x2650]` (the constructor copies interval 6 there in the shared tail `0x412468`) and creates an AnimSprite `blast_verysmall` frames 16..22, period 5, mode 6 (additive) at the step's point (call site `0x411952`). The landing step makes none. So the "beam" is a puff every 6 path pixels (speed 180 = 3 steps per tick) ending in the `flamerburst` of the impact. `effects::flame_trail`, `World::step_bullets`; tests `a_flamer_bullet_leaves_a_trail_of_puffs`, `flamer_trail_branch_matches_the_exes_flight_step`.

**Blue bolts of type 27** (1S special tier 1 and walker 5W1; the draw function `0x410a30` has no case for 27): the flight step has its own branch (`0x411bc2: cmp eax, 0x1b`) with the flamers' counter (interval 5, reloaded from `[+0x2650]`) that creates an AnimSprite `bodky_b` frames 4..6, period 1, repeated 3 times, additive (call site `0x411c2d`) at the bullet's position. Chained along the 600-step path they form the two blue streaks of walker 1's barrels. `effects::spark_trail`, `World::step_bullets`; test `a_type_27_bullet_leaves_blue_sparks_every_fifth_step`.

## Blit routines
Every draw call picks one of the exe's software blitters (RGB565, RLE sprites, clipped, colour-keyed). All kernels are now exact, ported as `effects::Blit::apply565` and checked pixel for pixel against the exe's own routines in the emulator by `scripts/verify_blits.py` (random RLE sprites, random destinations). Per channel (5/6/5-bit fields; "src/2" is the source field shifted right):
- `0x45edf0` plain copy; `0x461740` is *not* plain (see lens).
- `0x45cde0` (also `0x45e560` with a flag, and `0x45b5e0` which additionally needs the screen mask byte below `[0x49a33b]`, see "The screen mask"): `min(dst + src, max)`.
- `0x45c220` (draw mode 9): `min(dst + src/2, max)` - the source halved first (an additive glow at half strength).
- `0x4611f0` (modes 10 and 11): `(dst + src) / 2`, a 50 % blend rounded down.
- `0x45f4d0` (mode 14, the fighter's smoke): `max(0, dst - src/4)`; like `0x45b5e0` it only draws where the screen mask byte is below `[0x49a33b]`.
- `0x45df40` (mode 15, decals): `max(0, dst - src/2)`.
- `0x460f60` (shadows; bullet draw cases): the sprite is only a stencil (flag 1: its pixel words are skipped, flag 0: the file has none); each covered destination pixel is looked up in the 64K table `0x73ced8`, which `0x45d590` builds as `max(0, channel - 6/12/6)`. The same builder makes `0x71ced0` (-4/8/4), `0x75cee0` (the 6/12/6 table applied twice), `0x77cee8` (`min(channel + 1/2/1, max)`) and `0x79cef0` (a grey ramp, `5 bit = (r*299 + g*587 + b*114) / 1000 + 4`, clamped to 31, replicated into all three fields); the 555 variants of every routine exist for display format `[0x517aec] != 2`.
- `0x461740` (mode 13, "lens"): stencil sprite; each covered pixel becomes the picture pixel 2 columns right and 3 rows down (the loop stops at row `0x1de`), brightened through `0x77cee8`. `Blit::Lens`; `blit_blend` reads the offset pixel.
- `0x466140` is not a sprite draw: it is a DirectDraw blit that restores the background under a rectangle (dirty-rectangle erase), used by the `0x414020` pass.
- OpenSOW: the same RGB565 kernels in `render::blit_blend` / `blit_blend_masked` (`Blit::apply565` per pixel); it redraws the whole frame, so the erase passes are not needed, and the 555 variants are not ported (RGB565 only).

## Animation sprites (`AnimSprite`)

Explosions, smoke and markers are `AnimSprite` objects (class name survives in the vtable at `0x485e9c`; constructor `0x404cf0`, initialiser `0x4054a0`). `0x4054a0(x, y, period, array, from, to, repeat, flag)`: frames `from..to` of `array` repeated `repeat` times form a list (`[+0x24]`, length `[+0x3c]`); `[+0x10]` = `period` is how many logic steps each frame stays; `[+0x34]` is the draw mode set afterwards (6 for all explosions: the additive blit `0x45cde0`; the draw method `0x404e30` has a jump table `0x405080` over modes 1..15: 1-5 and anything else plain `0x45edf0`, 6 `0x45cde0`, 7 `0x45e560`, 8 `0x45b5e0`, 9 `0x45c220`, 10-11 `0x4611f0`, 12 a stack of plain-sprite draws, 13 `0x461740`, 14 `0x45f4d0`, 15 `0x45df40`); `[+0x1c]` flag. The update `0x4050d0` counts `[+0xc]` down, advances `[+0x38]` when it reaches 0 and removes the object when the index reaches the list length; mode 10 additionally moves the sprite up (rising smoke). `AnimSpec::frame_at(age)` is that rule.

`effects::SPAWNS` lists the 31 call sites with constant arguments and their trigger; all addresses are exe-tested. Highlights:
- building destroyed: turrets `e_turret` (45 frames, period 2), others `e_bubg` (83 frames), played at a random point of the footprint together with area damage and six debris bullets (types 13/14, docs/projectiles.md) - `destruction_burst` in the sim;
- air force unit destroyed: `e_air2` (52 frames); ground unit destroyed: see "Unit destruction" below;
- order markers `cross_as`, `cross_rp`, `click`; the walker teleport; the missile and meteor smoke trails; the fighter's smoke trail.

**Blasts** (`0x405240(x, y, size)`): `blast_verysmall, small, medium, big, blast2_defrag, blast2_artligh, blast2_artheav` = size 0..6; frames 22 (23 for size 4, 30 for sizes 5 and 6), period 4, mode 6. Which bullet type makes which blast (`effects::impact_blast`, from the impact function `0x40f590`): type 1, 6, 17 size 1; 2, 7 size 0; 3 size 5; 4 size 6; 11 size 4; 15, 16, 24, 25 size 2. The same function creates the type's own effect (`effects::impact_anims`): flame bursts (8, 9), `bomba_ex` (18), `fighter_ex` (26), `specialfall_*` (27-29), `bodky` fragments (19, 21).

## Impact sounds

The impact function plays one sound at the end point (table `0x410a14` -> `0x4109f0`, sound ids = `formats::sfx`): type 1 -> 20 (anti-air `strelba`), 3, 4 -> 21 (artillery `strelba`), 6, 7 -> 22 (cannon `strelba`), 15, 16 -> 28 (`unit-turet` explosion), 17 -> 26 (`sentry` explosion), 18 -> 65 (`hercules-boom`, only half of the time), 24, 25 -> 70 (`meteor`), 26 -> 67 (`stihac-boom`); other types are silent. So the three ground-unit fire sounds (20-22) play when the shell lands, not at the muzzle; the muzzle sounds are played when the volley is spawned (docs/audio.md, `sfx::muzzle`). `effects::impact_sound`.

## Smoke puffs and scorch decals

Both come from the generic tail of the impact function (`0x410405`, reached by every bullet type except the targeted hits 1, 10, 31, the Tripler pod 17 - which has its own code - the bodky types 19-21 and 22). `effects::impact_leaves_decal`, `impact_smoke`, `smoke_puff`, `DECAL_ARRAY`; the game's `World::impact_ground_effects`.
- **Decal** (class vtable `0x487b04`, init `0x41a1d0(x, y, frame)`, draw `0x41a160`): when the landing cell is strictly inside the map (`0 < cx < width`, `0 < cy < height`), free (no building, no terrain block: map `ground` layer `+0x80cc` is 0), not marked **no-marks** (map layer `+0x2c0cc`, only M02 has any: 497 cells, `map::Cell::no_marks`) and has no decal yet (flag grid `0x513878`), a decal with frame `random(9) / 2` (visual generator `0x437cd0`) is added to the list `[0x49a3d0]`. It is drawn from sprite array `0x5e6960` (`__extras\pustkrat`, 25 frames, variant 0-4) with the darkening blit `0x45df40`, and removed (its flag cleared) once a building stands on the cell.
- **Puffs** (`0x405340(x, y)`, list `[0x49a3a8]`): an `AnimSprite` with period 5, mode 8 (blit `0x45b5e0`), flag 0; the sprite is `fire_sm1` or `fire_sm2` (`random(2)`), frames 0-8 once and then `4 + random(13)` more passes (45 to 153 frames, 225-765 ticks). Where they appear, at offsets -10..9 px (the first draw is added to y, the second to x): type 17 and 18 impacts make two, only on a cell that is free **and** not no-marks (`0x40fc0a`, `0x40fe18`; visual generator). In the generic tail the exe always rolls `random(3)` (lockstep `0x437b10`) after the decal test, then (`impact_smoke`, `0x4104da..0x4106fb`): ground not free -> nothing; roll 1 and type 15/16 -> **three** puffs with offsets from the *lockstep* generator (`0x410510`, `0x41059b`, `0x410629`; six more draws), which then fall through into the single puff below; every other case of types 13 to 16 (also roll 1 with 13/14) -> **one** puff if the cell is also not no-marks (`0x4106ba..0x410752`, offsets from the visual generator). A type 15/16 hit on a roll of 1 therefore makes four puffs on ordinary ground. (An earlier note said three, and none for 13/14 on roll 1.) A destroyed ground unit makes three (`0x46af25..0x46b047`, lockstep generator, offset by the chassis hover height).

**Differs from the exe:** the visual generator `0x437cd0` (a C `rand()` table) is an xorshift in OpenSOW (`World::fx_random`), so decal frames, puff sprites and offsets, the Tripler ring jitter and the wreck smoke targets have the exe's ranges but not its sequence. The lockstep draws (`0x437b10`) are the exe's (`rng.rs`).

**Blit routines settled**: `0x45df40` = `max(0, dst - src/2)` per channel (decals), `0x45b5e0` = the additive blit but only where a screen mask byte `[0x6b3cd4 + ...]` is below `[0x49a33b]` (see "The screen mask"), `0x45cde0` additive, `0x45edf0` plain. All blit kernels are exact now (see above).

## Unit destruction (`0x46a560..0x46b0f0`)
`effects::UNIT_DEATH_CLOUDS`, `debris`, `UNIT_DEATH_SOUND`; exe-tested by `unit_death_matches_the_exes_destruction_code`; `World::step` uses them. In order, for a unit of kind `k` at `(x, y)` (turret kinds 109-113 take a separate path that just frees the handle):
1. **Four clouds** (`e_unit2`, period 3, additive, flag 1) at `(x - 15 + rand(30), y - 15 + hover + rand(30))`; two lockstep draws each, the first for y, the second for x. The Advancer (kind 40) makes the same four; every other kind has the `newvrak` wreck inserted after the second cloud at `(x, y + 7)` (period 5, default blit).
2. Sound 27 (`explodes\unit`) at the unit through `0x4077e0`.
3. **Flying pieces** for kinds 1-15 and 41-45 that have a top part: a bullet of type 15 (blue unit) or 16 (green), from `(x, y + top height)` to `(x + sx, y + sy)`, `s = (2 * rand(2) - 1) * (rand(spread) + spread)` for each axis; `spread` is 30, 40 or 60 by weapon tier (`(k - 1) mod 3` for kinds 1-15, 60 for the walkers). **Strength 40** (constructor argument 2 -> `[bullet+0x2660]`; an earlier note read the `push 0x28` as a path delay, the delay stays 0), so the landing piece runs the area damage `0x42f2c0` like a shell (generic tail `0x410881`: ground units within 32 px and the building in the cell lose 40, friend or foe). **Variant** `[bullet+0x2680]` = the top sprite index `[top+0x54]` = `tier * 5 + class` (jump table `0x46b140` is the identity for 0..=14), the piece's `blueboom`/`grenboom` frames are `variant * 80 + counter`; tops with an index above 14 (the walkers' `5W1..5W5` = 20..24, the Advancer's `1I`) skip the bullet, **after** the four lockstep draws are made. Bullet class `+0x265c` = 2, 2, 3 by tier; the third class value (2, 3, 4) is the **death variant** stored at `unit+0x94` by `0x46b0af` (`0x46a5b3` first sets it to -1; kinds without a debris class keep a non-matching value) - see "Corpses" below. Skipped when `0x41f020(player)` says the local side does not own the unit (network clients). `effects::DEBRIS_STRENGTH`, `debris_variant`; the game gives the piece strength and variant.
4. Except for the Advancer: the **burning wreck** object and three smoke puffs (`UNIT_DEATH_PUFFS`). The wreck (`0x45afc0`, 0x1c bytes, vtable `0x490100`, list `[0x49a3e4]`, init `0x45b210(x, y + [chassis+0x2c], 0, 0, 20, 5)`) is updated by `0x45b0a0` once per logic step: remove when its counter `+0x14` is 0 (20 at the start), else decrement the countdown `+0x18` (5 at the start); at 0 reload 20, decrement the counter and throw a bullet of type 22 (the fighter's smoke sprite, speed 20, strength 0, owner 0) from the wreck to `(x + 80 + rand(80), y - 80 - rand(40))` (visual generator, x first). So 20 smoke columns leave at steps 5, 25, ..., 385 and the object ends at step 386 (`effects::WRECK_SMOKE_*`, `World::step_wrecks`; read from the disassembly, not emulated).

OpenSOW: same, the wreck starts at `y + [chassis+0x2c]` (`sim::draw_offsets`, unit death in `sim.rs`).

## The screen mask (`[0x6b3cd4]`, `0x459450`, `0x460120`)
A byte per screen pixel (`(height + 0x1a) * width + 0x64` bytes, allocated with the display `0x42c3ed`) plus a generation byte `[0x49a33b]`. Once per frame `0x459450` increments the generation; when it passes 250 the buffer is cleared (`0x45d530`) and the generation restarts at 1, so nothing is cleared per frame. **Writers** stamp the generation into the mask: `0x460120` draws a sprite's *shape* into it (no colour), called for every building's `builds\mask` frame (`0x4093e8`, `0x45888c`: array `0x5e4520`) and for each foreground tile of the `.til` set (`0x459666`: array `0x5de440`, the tree and rock tops that stand in front of the ground). **Readers** draw a pixel only if its mask byte is below the generation, i.e. only where nothing was stamped this frame: `0x45b5e0` (AnimSprite mode 8, the smoke puffs), `0x45f4d0` (mode 14 and the bullet draw of type 22: smoke trails, the burning wrecks' columns) and the flagged ground-unit blits. So smoke is hidden behind building fronts and tree tops, while the additive explosions (modes 6, 7) are not. The body of a ground unit is drawn with the *unmasked* plain blit (`0x46e8f0` passes flag 0; only menu code uses `0x45edf0` with the mask flag), so units are not hidden by the mask in the exe. What does read it among the unit parts is the **shadow of a weapon top** (`0x46e9c0` -> `0x462110`, the shade table `0x73ced8` where the mask is below the generation), while the chassis shadow (`0x46e980` -> `0x460f60`) does not. The game builds the same mask per frame (`Play::screen_mask`: `render::stamp_foreground` for the foreground pixels and `stamp_frame` for each building's mask frame) and uses it for those two routines (`render::blit_blend_masked`) and for the top shadows (`render::blit_shadow_masked`); `AnimSpec::mode` / `routine()` carry the mode.

**Differs from the exe:** the game redraws buildings over ground units through their mask frames and draws the foreground tile rows after the units in them (`Play::finish_ground`, docs/art.md "Foreground tiles"), so buildings and tree tops hide units.

**Frame order** (`the_frame_draw_order_stamps_the_mask_before_the_smoke_and_the_top_shadows`, call sites in the exe): the main loop `0x42d6b0` runs the map pass `0x459350` (it bumps the generation `0x459457`, stamps the foreground tiles `0x459666` and draws the *static* buildings `0x45969d` -> `0x4586a0`, whose loop stamps each building's mask `0x45888c`) and then the world pass `0x41f690`, which runs in this order: (1) the smoke puffs, list `[0x49a3a8]` (`0x41faf7`, draw mode 8, masked by the tiles and static buildings stamped so far), (2) the live buildings `0x4092f0` (animated ones draw and stamp here, `0x4093e8`), (3) the ground units (`0x46a3a0` tops: the masked shadow, then the body), (4) aircraft and the Advancers' shadows, (5) the explosion list `[0x49a394]` (blasts, missile smoke, sparks, `0x420105`) and a second AnimSprite list (`0x420147`), (6) the bullets `0x410a30` (the wrecks' smoke), (7) the Advancers' bodies `0x46a310`. So the puffs lie *under* the units and live buildings, the missile smoke, wreck smoke and top shadows are masked by every stamp, and the mask was complete before all of them. The game draws the puffs first in `draw_units` (before the units, `Play::draw_puffs`) and the rest in `draw_shots`; it stamps every building up front.

**Differs from the exe:** the exe stamps the live-animated buildings only after the puffs are drawn, so puffs are not masked by them there; OpenSOW masks the puffs by every building.

Check: `scripts/verify_screen_mask.py [WxH]` renders five areas (M01 player base, enemy HQ, a factory, M03, M06) with and without smoke and with `--no-mask`; the masked picture equals the baseline on every pixel the mask hides (about 1600 of 5100 smoke pixels per area) and shows the rest; with a grid of units around the same spot every pixel the mask changes is a darkening (the unmasked picture is never brighter), 2450 pixels over the five areas, so the top shadows are hidden over building masks and tree tops. The numbers are the same at 640x480, 1280x800 and 1920x1080 (the view does not scale with the window).

## Shell smoke trails
Types 1, 3, 4 (artillery) and 24, 25 (meteors) leave smoke while they fly: `effects::trail`, exe-tested by `shell_smoke_trails_match_the_exes_flight_step`; in the game `World::step_bullets` (`--fx CX,CY,missile,0 --ticks N` headless). The missile's and the shells' smoke is `missileSmoke` in draw mode 14 (`0x45f4d0`, darkening, masked); the meteors' smoke uses mode 6.

## AnimSprite draw modes (`0x404e30`, jump table `0x405080`)
The mode `[obj+0x34]` is stored by the creator after the initialiser (which sets 0): `effects::ANIM_DRAW_MODES`, exe-tested. 0..=5 plain `0x45edf0`; **6** additive `0x45cde0` (blasts, sparks, almost everything); **7** `0x45e560`; **8** `0x45b5e0` (puffs); **9** `0x45c220` (fighter smoke); 10 and 11 `0x4611f0`; **12** a column; 13 `0x461740`; **14** `0x45f4d0` (missile smoke); 15 `0x45df40`. The creators store only the immediates 0, 6, 8, 9, 14 and, from `[0x49a33a]`, 6 or 7 (building and air-force destruction), so modes 1-5, 10-13 and 15 never occur. **Mode 12** draws the current frame 14 times additively at `(x, y - 23 - 46 * k)` (`effects::ANIM_COLUMN`): the satellite laser's column as an `AnimSprite`, an unused leftover; the real laser is the bullet's own draw (below).

## Satellite laser (bullet type 10, `0x411100`, `0x409f50`)
Fired by the protected building's check (docs/advancer-actions.md) at each foreign Advancer above its footprint, which is killed in the same call (`[unit+0x34] = 0`): strength 1000, from `(x, y - 64 - 15)` to `(x, y - 64 + 10)`, owner = the Advancer's team, homing handle `[+0x2688]` = the Advancer. The impact (`0x4108bc`, shared with types 1 and 31) only subtracts the strength from that handle's unit and makes no area damage, decal, blast or sound, so the bullet is purely visual. Its draw (called from `0x4203e2`; `0x414190` is the variant that uses blit `0x466140`) ignores the bullet's position and draws at the path's **end** point: one `satlaser` frame `counter + 4` at `y_end - 23`, then 13 frames `counter` going up in 46 px steps, additive (`0x45cde0`), skipped when the base is outside the 480-pixel view; the counter `[+0x2670]` runs 0..3, 4 steps per frame. `effects::satlaser_column`, `SATLASER_*`; exe-tested by `satellite_laser_column_matches_the_exes_draw`; `World::step_satellites` fires it, `play.rs` draws it (`--fx CX,CY,satlaser,0` headless).

**Differs from the exe:** OpenSOW has no 480-pixel test: the column is drawn (and clipped) whatever the window height (`Play::draw_shots`).

## Corpses (`unit+0x90/0x94/0x98`, `0x46a5a9`, `0x46b600`)
A destroyed unit does not leave its slot at once. The death handler sets `+0x90 = 430` (the timer), `+0x94 = -1` (variant, filled in at the end of the destruction code with the debris class's third value: 2, 3 or 4 for tiers 30/40/60 px) and `+0x98 = 0`. The unit tick (`0x46dfc7`) then, while `unit+0x2c == 1` (dead): stamps its own cell `(x>>5, y>>5)` of the unit grid with the terrain marker `0xFFFFFD` **every step** (air grid `0x60ac38` for the Advancer, else `0x5eac38`), so a **corpse blocks its cell for 430 steps** (about 7 s), and calls `0x46b600`: timer -= steps; once it is below 30 (flag `+0x98` set, so only once) it throws the final blasts, `0x405240(x, y, size)` at `(x - 15 + rand(30), y - 15 + rand(30))` (lockstep draws, y first): variant 2 two blasts of size 2, variant 3 three of size 2, variant 4 one of size 3 then three of size 2 (kinds without a debris class: none). The slot is freed when the timer goes below 0. `effects::CORPSE_LIFE`, `CORPSE_BLAST_BELOW`, `corpse_blasts`; test `unit_corpse_timer_and_final_blasts_match_the_exe`; `World::step_corpses` and the occupancy grid use it.
