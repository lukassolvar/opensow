# Art lookup (what the viewer draws)

All names are inside `sprites.data` (see `MegaFile`); the `Data/units` folder only has a loose copy of `units\*`.

## Buildings: `builds\{blue|green}\{stem}.ps6`, shadow `builds\shadow\{stem}.sha`, footprint-ish mask `builds\mask\{stem}.msk`
Stems: `_base _light _med _heavy _air _mine _rlab _wind _walker` (kinds 100..108, see `docs/levels.md`).
- Frame layout (blue set, 18 frames for most): 0 scaffold, 1 construction, 2-14 idle animation (13 frames; e.g. the lab's eye lights up),
  15 damaged, 16 destroyed, 17 grey = neutral/uncaptured. `_air` has 28 frames (last = neutral, 25 damaged, 26 destroyed), `_walker` 14
  (13 neutral, 12 destroyed), `_base` 7 (0-4 upgrade stages, 5 destroyed, 6 = preview picture on a solid background; never neutral).
- Animation (`buildings::anim`, constructor 0x40a330, draw 0x4092f0, tick 0x40df00..0x40e0d9): per building a state `[b+0x48]` picks a frame range
  from boundaries `[b+0x28..0x44]` (0 scaffold, 1 construction, 2 just finished, 3 = the idle loop, 4 damaged = hp <= max/2, 5 destroyed, 6 neutral).
  During the build-up (`[b+0x68]`) the state is hp in thirds (0/1/2). The loop frame `[b+0x4c]` advances every `[b+0x58]` ticks (60/s):
  light/medium/heavy factory and wind trap 2, air base and gold mine 6, lab and walker factory 4; the HQ has no loop (all single frames).
  Loop length: 12 frames (air base 22, walker factory 8). Single-frame states are painted once into the background. Viewer `--walk TICKS` shows the loop at a tick; the game animates live.
- Green (enemy) sets are the same art recoloured with one trailing frame fewer. Neutral uses the blue set's last frame.
- Shadows: same index as the sprite; use frame `min(idx, len-1)`; draw before sprites at ~40 % black. `.sha` hot spots are relative to the same anchor.
- Anchor: the sprite hot spot goes at the centre of the object's cell (`cell*32+16`). Verified on M01 (HQ, factories, lab sit correctly on terrain).
- `.msk` files use the same frame layout (Kind::Shadow): the building's shape, stamped into the exe's screen mask (docs/effects.md "The screen mask"). OpenSOW loads them as `BuildArt::mask` and also uses them to draw buildings over units (see "Foreground tiles" below).
- Visuals: `_air` looks like a radar dish tower, `_walker` a flat round pad, `_wind` a tall rotor.

## Turrets = base + gun top (`buildings::turret_art`, exe-tested)
- A turret building (kinds 25-29) is a static base, `builds\{blue|green}\sentry01` (kind 25), `sentry02` (26, 27), `sentry03` (28, 29; 6 frames: scaffold, construction, finished, working, damaged, neutral; `anim`), plus a **separate unit** of kind 109-113 that the exe creates once the turret has healed in (`0x40e004`; for 28/29 one cell lower). The unit is only a weapon top; it turns, recoils and looks around randomly like any unit top (docs/art.md Idle look-around).
- The sprite number is **not** the turret number (top constructor field `[+0x54]`, vertical offset `[+0x60]`): turret 1 Guard Cannon = `tur_02` (-11), 2 A.A. Defence = unit top `2AA` (-2), 3 Plasma = `tur_03` (-20), 4 = `tur_01` (-17), 5 = `tur_05` (-31). Earlier notes assumed `tur_0N` for turret N and drew no base.
- OpenSOW: same (`turret_art` in `opensow_viewer::art` and `play.rs`; the gun top only once the turret has healed in, `step_structure`).
- `tur_01` has 96 frames (3 phases x 32 facings), the others 32; frame = phase*32 + facing. `units\turrets_shadow.ps6` has only 3 big frames; not mapped to turrets yet.

## Units = chassis + top (decoded from the exe; implemented in `opensow-formats/src/units.rs`)
- Files: `units\{name}_{blue|gren}.ps6` and `.sha` (shadow); loose copies also in `Data/units`.
- Chassis index per kind (`0x46ff50`, draw `0x46e8f0`) into `chA chB chC chI1 chW chN`: ground tier 1/2/3 -> `chA/chB/chC` for every class (an earlier note that kind 6 used `chA` was a mis-read: the extraction ran past the end of its case),
  Advancer (40) -> `chI1`, walkers (41-45) -> `chW`, kind 46 -> `chN`.
- Top index per kind (weapon ctor byte table `0x47ac70`, draw `0x479a80`) into `1AA 1A 1C 1F 1S 2AA..2S 3AA..3S 1I tur_01 tur_02 tur_03 tur_05 5W1..5W5`:
  `index = (tier-1)*5 + class` for ground units, 40 -> `1I` (a 16x2 empty placeholder), 41-45 -> `5W1..5W5`, 46 -> none.
- Frames: chassis `chA/B/C` have 6 animation rows x 16 facings, `chW` 10 rows x 16, `chI1` 2 x 16; tops 2 x 16 (walker tops 16). 16 facings run clockwise from north.
  The engine indexes `chassis[type*200 + frame]` and `top[idx*150 + facing*[obj+0x50] + [obj+0x6c]]`. Markers have no facing; the viewer defaults to 0 (north), see the Facing section.
- Weapon offsets `.po1/.po2` are decoded (`fire.rs`, below). They are muzzle/fire points, not mount offsets: the top is drawn at the same anchor as the chassis
  and that looks right for tanks and walkers (M01, M03, M06, M15). Fields `[obj+0x5c/0x60]` of the top object are decoded: `dx` is always 0, `dy` = `aim::top_dy(kind)` (-4, -10, -16, 0 by kind from the shared constructor tail through byte table `0x47acf4`, plus a base for kinds 2 (4) and 12 (7) and the turret tops). They are the **aim origin** (`0x4797c0`: chassis position + `(dx, dy)`) and place the muzzle-flash rectangle (`0x479bc0`), not the sprite draw. The game uses `top_dy` for the aim facing of ground units, the anti-air units and the Advancer (turrets did already).
- Verified visually: cannon tanks (M01, M15), walkers with different tops (M03), hazard pods (M03), Advancer next to the HQ (M01).
- Test: `tests/real_data.rs` checks every unit kind placed in the campaign has both team sprite files.

## Flying units
Air forces are drawn from `specials\` (docs/air.md), not `units\`.

## Weapon fire points: `units\{top}.po1` / `.po2` (`opensow-formats/src/fire.rs`, viewer overlay `F` / `--overlay muzzles`)
- A file = tables of 32 `(i16 dx, i16 dy)` points, one per top facing (frames 0..31 = 2 rows of 16, clockwise from north). `.po1`: one table per barrel/simultaneous shot
  (`size/128`: 1 for most, 2 for twin AA `1AA`, 6 for `3AA`, 2-4 for walkers, up to 3 for `tur_05`); `.po2`: exactly one table (the weapon reference point; identical to `.po1` for single-barrel tanks).
- The spawner `0x47cf70` (loaders `0x437f10`, arrays `0x70efb8`/`0x70efa4` indexed by top) starts a shot at `unit position - po1[variant*32 + facing]` and derives its direction from `po2 - po1`.
  So `muzzle = anchor - po` in screen pixels, y down. Points trace a squashed circle around a pivot ~16 px above the anchor (1C: `po1[8] = (-20,-1)` -> muzzle 20 px right).
- Verified visually: red points land on barrel tips for cannons (M15), artillery and twin AA (M06: two points per AA unit) and on both walker arms (M03).
- Unused barrel slots in walker files are all zeros. `1I` (Advancer, no weapon) is a constant (0, 2). `tur_04.po1/po2` exist even though turret 4 has no sprite (it shares `2AA`/`tur_04`-style tables with the satellite laser).
- The facing is derived from the heading by `facing::facing()` (decoded, see "Facing and frame selection"). Not traced: what `po2 - po1` does for single-barrel units (zero vector; probably the target direction is used instead).

## Facing and frame selection (`opensow-formats/src/facing.rs`; viewer `--facing N`, keys `[` `]`)
- Facings are numbered **clockwise from north**: with 32 steps 0 = north, 8 = east, 16 = south, 24 = west. Verified in the viewer: at facing 0/16/24 cannon barrels point up/down/left and the red muzzle points sit on the tips.
- Heading -> facing is `0x46b180(ax, ay, bx, by, steps)`: atan of `|dy|/|dx|` in degrees with `dx = bx - ax`, `dy = ay - by`, quadrant-corrected to a counter-clockwise angle from east, then `(8 - round(theta/11.25)) mod 32` (16 steps: `(4 - round(theta/22.5)) mod 16`).
  Ported faithfully, including two original quirks: for 16 steps the wrap-around sector (heading just below east) returns 5 instead of 4, and a == b (NaN) returns the table default (8 for 32 steps, 0 for 16). The 8-step mode is live: `(2 - round(theta/45)) mod 8` (0 N, 2 E, 4 S, 6 W), default 2; verified by emulating the exe.
  A test reads the exe's own jump tables and compares every sector (`facing_port_matches_the_exes_jump_tables`); `scripts/verify_against_exe.py` additionally emulates the whole function.
- Turning (`0x46a190`): one facing step toward the target along the shorter arc per call; a tie goes backwards. A chassis keeps its current facing at `[obj+0x30]`, the target at `[obj+0x34]`, a turn-delay countdown at `[obj+0x38]` (reload `[obj+0x3c]`).
- Frames: chassis `frame = phase * steps + facing` (`0x46fe80`; `[obj+0x44]` = animation phase, `[obj+8]` = steps, default 32). `chA/B/C` = 3 phases of 32 (96 frames), `chW` = 5 phases (160), `chI1` = 1 (32).
  Tops: `top[idx*150 + stride*phase + facing]` (draw `0x479a80`), stride 32 (16 for the 16-facing walker tops 5W1-5W3, 5W5); `2A/2C/3A/3C/tur_01/5W4` have 2-3 phases of recoil frames (64/96/48 frames, see Recoil below).
- Fire points for 16-facing tops are indexed by the top's own frame (their `.po` tables fill only the first 16 entries); 32-facing tops use the 32-step facing.
- A unit's initial facing (unit initialiser `0x46bd30`; chassis and top are `operator new` objects, not zeroed): the chassis initialiser `0x46ff50` writes facing `[obj+0x30]` = 8 (`0x470361`) and target `[obj+0x34]` = 0 (`0x470397`); the top initialiser `0x479eb0` writes target `[top+0x70]` = 0 (`0x479f02`) and its shared tail facing `[top+0x6c]` = 15 (`0x47abb5`), for every kind (`sim/unit_defaults.rs`, generated by `scripts/gen_unit_defaults.py`). So a new unit turns towards north right after it spawns: the chassis from 8 (east with 32 facings, south with the 16 of walkers and pod), the top from 15. The viewer draws markers at `--facing 0`.
- OpenSOW: same; `World::add_unit` (`sim/setup.rs`) starts the chassis at 8 with target 0 and the top at 15 with target 0 (test `a_new_unit_starts_like_the_exes_initialisers_and_turns_to_north`); a savegame import keeps the stored facings (`sim/savestate.rs`).
- Recoil timing is decoded (`recoil.rs`, "Fire and recoil"); the death sequence is docs/effects.md "Corpses". Not traced: the Advancer's frame counter `[obj+0x40]` (up to 31 at `0x46f22e`, one facing step per 3 ticks, see below).

Viewer: key `N` / `--overlay minimap` draws a minimap in the top-right corner (`render::draw_minimap`: blocked cells, every object in its owner's colour, unit markers, the camera rectangle; 1-6 px per cell by screen size).

## Walk animation (`opensow-formats/src/anim.rs`; viewer `--walk TICKS`, key `K`)
- Chassis tick (`0x46f8b9`, `0x46fe00`): turn first (counter `[0x38]`, reload `[0x3c]` = 4, 0 for the Advancer; one `turn_step` every `reload+1` ticks), and only once the facing equals the target does the animation counter
  (`[0x4c]`, reload `[0x50]` = period) run; each expiry advances the phase `[0x44]` **if the unit moved** and wraps it at `[0x48]` phases. `frame = phase*steps + facing`; the Advancer's frame is not updated.
- Per-kind values (all verified against the exe by `tests/real_data.rs`): ground kinds 1-15 have 3 phases and periods 8,8,11,7,8,**1000**,5,6,10,4,8,11,7,8,12 (kind 6, tier-3 artillery, never sets one and effectively does not animate);
  walkers 41-45 have 10 phases, 16 facings and periods 8,6,6,6,6; the pod (46) has 3 phases, 16 facings and period 3 (13 when the game-mode global `[0x49a33c]` is 3 or 8, which also drops its speed field to 7); the Advancer (40) has none.
  `steps = frames / phases`: `chA/B/C` 96/3 = 32, `chW` 160/10 = 16, `chN` 48/3 = 16, `chI1` 32.
- Field `[obj+0x18]` = **walking speed in pixels per second** (decoded): kinds 1-15 = 18,14,10 / 15,12,8 / 22,18,14 / 20,17,12 / 16,15,10 (tiers 1-3 of five classes), Advancer 30, walkers 41-45 = 20,15,20,15,20, pod 46 = 30 (7 in game modes 3/8). The unit step (`0x46f140` -> `0x46f550`) runs once per tick with the tick-in-second index (0..59) and pops `steps_at(speed, idx)` points from its path (`[obj+0x9c]`, count `[obj+0xa0]`); the path is a list of **single pixels**: `0x46ee80` fills it with a Bresenham line between waypoints (cell centres `cell*32+16`), so diagonals cost the same as straight moves (Chebyshev, not Euclidean). It moves only when the chassis is within 4 turn steps of the wanted facing; the route is re-planned every 7 ticks (`[obj+0x80]` counter, `0x46eb40`/`0x4753a0`). Tier-1 cannon (kind 7) = 22 px/s = 0.69 cells/s. Test: `walk_parameters_match_the_exes_chassis_initialiser`.
- All counters are in game ticks: 16.66 ms, 60 ticks/s (docs/executable.md); the game runs at that rate. OpenSOW: `anim::ChassisAnim`, driven by `World::step_unit`.
- **Differs from the exe:** the viewer's walk/fire preview (`--walk`, `--fire`, keys `K`/`V`) runs at 20 ticks/s (`PREVIEW_TICKS_PER_SECOND`, `opensow-viewer/src/main.rs`).
- Verified visually: walker legs alternate across the five phases; tank track detail changes subtly.
- "Moved" (decoded): `0x46f550` calls the chassis tick every step, with pointers to the unit's own position `[unit+0x14/0x18]`; the tick (`0x46f906`) advances the phase when that position differs from `[chassis+0x5c/0x60]`, the **goal pixel of the current order** (written by the order code `0x47056b..0x473469` and `0x46ee3d`; when the unit stands on it with no route left `0x46f5b1` pops the order, `0x46f950`). So legs move while the unit has somewhere to go, **also when it waits for a free cell** (the old port advanced only on ticks where the position changed, which skipped the sub-pixel ticks of slow units); a unit at rest does not animate. `World::step_unit` uses "has a route".

## Fire and recoil (`opensow-formats/src/recoil.rs`; viewer `--fire TICK`, key `V`)
- A weapon top (object built by the constructor at `0x47a000`, state machine `0x479c60`) has a state at `[obj+0x48]`: 0 looks for a target every 30 ticks, 3 aims (waits until its facing equals the target facing), 4 plays the fire sequence, 6 is the finished state.
- The sequence is a list of **steps**: `(phase, flash_group, barrel, shots)`, added by `0x479760` in each kind's constructor case after an implicit rest step 0. Each step lasts `reload + 1` ticks (`[obj+0x210]`, default 10); the first step starts on the first tick of state 4; shots fire on a step's first tick; after the last step the override ends.
  `phase` = which phase block of the top sprite (`frame = phase * steps + facing`): the barrel slides back for phase 1 (2A, 2C, 3C) and 3A uses phases 1, 0, 2. `flash_group` = group of 32 facings in `units\{top}_fire.ps6` drawn at the top's anchor on top of it, **additively** (`0x479a20` -> `0x45cde0`; drawn plain the sprite's black background shows as a dark ring) (the `_fire` sets are `1A 1C 2A 2C 3A 3C tur_01 tur_02 5W4`, `[obj+0x58]` = index).
  `barrel` + `shots` select `.po1` tables: a step fires tables `barrel .. barrel+shots-1` at once (3C fires 3 shots from its 3 tables; the 6-barrel 3AA fires barrels 0..5 one per step).
- Examples (reload): 1AA/2AA/3AA alternate barrels with no flash (15); 1A flash groups 0,1 (5); 2A phase 1 with groups 0,1 (10); 3A two volleys of phase 1 then 2 with groups 0..3 (10); 1C two flash groups (10); 5W4 phases 0,1,2 with groups 0,0,1 (reload 2); flamers and `S` tops have no flash or phase change.
- Verified: every table row is rebuilt from the exe's bytes by `fire_sequences_match_the_exes_top_constructor`, and cross-checked against sprite frame counts (phases, `_fire` groups) and `.po1` table counts. Visually: 1C shows a large then a small flash at the muzzle point; 2A's barrel is retracted while firing and extends afterwards.
- Idle: no top has an idle animation (the idle phase array `[obj+0x94]` holds a single 0).
- Not covered: kind 40 (Advancer, `1I_fire` is an empty 32-frame placeholder) and the static turrets' own sequences; damage and projectile motion. State 6 and the volley delay are decoded in Aiming below.

## Top aiming and the fire cycle (`opensow-formats/src/aim.rs`; viewer `--aim N`)
- The weapon top keeps its **own facing** (`[obj+0x6c]`, target `[obj+0x70]`), independent of the chassis; with `--aim` the viewer shows a turret facing another way than its hull (verified on M15 cannons).
- Per tick: (1) cooldown base class (`0x47c6b0`): a counter above `2*reload` resets to `reload`; in state 6 it counts down and returns the state to 0 at 0. (2) aim (`0x4797c0`): when the state is not 0 and a target exists the target facing is `facing(top pos + [0x5c/0x60], aim point, steps)`; the aim point is the building centre, or the unit position (flying units: plus half the height from a table at `0x89cf58`). A counter (`[0x74]`, initial 4, reload `[0x78]` = 4) then turns the top one `turn_step` per 4 ticks.
  (3) state machine (`0x479c60`): 0 polls for a target every 30 ticks (counter `[0x80]` reloaded with 30; starts at 0 so the first tick searches); a hit sets the cooldown counter to `reload - jitter/2 + random(jitter)` (`0x47c5f0`) and enters 3. 3 -> 0 if the target is gone; 3 -> 4 when `facing == target facing`. 4 plays the fire sequence, then 6 (cooldown), which counts down to 0 and returns to 0.
  Example (1C cannon, facing 0, target at facing 8, tick 1 = acquire): turns on ticks 4, 8, ..., 32 (8 steps); fires from tick 33; the 22-tick sequence ends on tick 55; cooldown 72 ticks puts it back to idle on tick 127, which re-acquires immediately.
- **Top follows the chassis** (decoded from `0x46f4a0`, `0x46f550`, setter `0x479980`, idle loop `0x46e114`; `aim::TopAim::set_target_facing`, `ChassisAnim::tick` returns "turned"): the top draws only `[top+0x6c]` and `0x4797c0` turns it one step per 4 ticks toward `[top+0x70]`, whatever the state. Nothing recomputes `[top+0x70]` from the hull; instead **every chassis turn step** (the `0x46a190` call, in both the idle step `0x46f4a0` and the walking step `0x46f550`) is followed by `0x479980(chassis target facing [chassis+0x34])`, which stores it in `[top+0x70]` **only if the top's state `[top+0x48]` is 0**. So a walking tank's top turns with the hull's heading (it lags by a few ticks), an aiming/firing/cooling top (states 3, 4, 6) ignores the hull and tracks the enemy. When the state returns to 0 the top keeps the enemy's facing until the hull next takes a turn step (a unit walking straight on does not turn, so its top stays pointed back at the old target; faithful quirk).
- **Idle look-around** (unit loop `0x46e114..0x46e198`, skipped for the Advancer): for a unit whose chassis has no order (`[chassis+0xe0] == 0`; or without a chassis, top state 0) a counter `[unit+0x8c]` counts down; at 0 it is reloaded with `240 + random(900)` ticks and, if the top is in state 0 with no target (`[top+0x7c] == 0`, `[top+0xc] != 0`), `[top+0x70]` = `random(steps)` (`steps` = `[top+0x50]`, 32 or 16). Skipped in network games (`0x41f020`). Spawn facings: see "Facing and frame selection". The initialiser `0x46bd30` starts the counter at `240 + random(900)` (lockstep generator, `0x46c10c..0x46c121`). OpenSOW: `World::step_unit` (`sim/movement.rs`), turret tops in `step_structure` (`sim/combat.rs`).
- OpenSOW seeds `Unit::look` with `240 + random(900)` in `World::add_unit` like the initialiser. Turret guns seed theirs (`turret_look`) the same way on their first tick after healing in, when the exe creates the gun unit. The counter runs while the chassis has no order (port: no route); a turret gun (no chassis) only while its top is idle (`[top+0x48] == 0`); at 0 both draws `rand(900)` and `rand(steps)` are made (a unit without a top makes only the first, `0x46e16f`) and the facing is taken only by an idle top without a target. **Differs from the exe:** "no chassis order" is the port's "no route and no straight order".
- The 5th argument of the top update `0x479c60` (`[chassis+0xe0] == 2`, the current order type 2 = the Advancer's beam approach) blocks the target search in state 0; irrelevant for ground tops.
- Per-kind values (`[0x18]` min range, `[0x1c]` max range in cells, `[0x28]` reload, `[0x2c]` jitter; jitter is 0 where a case never sets it, assuming zeroed allocation) are in `aim_params` and verified against the exe (the cases are decoded by following their jumps):
  anti-air 0-9 cells (reload 120 +-12, all three tiers); artillery 2-8, 3-9, 4-10 (72); cannons 0-6, 0-7, 0-8 (72); flamers 0-4, 0-5, 0-6 (reload 2); special 0-5, 0-6, 0-7 (180 +-18); walkers 5W1 2-8 (18 +-1), 5W2 2-9 (180 +-18), 5W3 2-6 (0), 5W4 2-11 (2 +-0.5), 5W5 0-1 (180 +-18). Walker tops have 16 facings. Projectiles: `docs/projectiles.md`.
- Target choice (`0x46c990` -> `0x47b140`): cells from the minimum to the maximum range are scanned in rings (the offset list built at `0x436230`, reproduced in `rings.rs`, see docs/projectiles.md "Range rings"); the current target is kept if still found, else the nearest unit, then a turret-like building (types 3/6), then any building (the manual's "units, turrets, buildings"). Which search runs is chosen in `0x46c990`: `[unit+0x4c]` (kinds 1, 2, 3, 42, 110; unit handle type 5/6) -> `0x47b3c0` (aircraft) then `0x47ad30`; `[unit+0x4b]` shooter -> `0x47aed0`; else `0x47b140`. Units are stamped into separate grids by `[unit+0x4b]` (`0x46f7ff`): ground `0x5eac38`, flyers `0x60ac38`. Only the Advancer (kind 40, case at `0x46bf95` sets `+0x4b`) is a flyer, so `0x47b140` can never see it; `0x47ad30` scans the air grid for enemy units, so only anti-air shooters (missile tank/robot, anti-air turret) fire at the Advancer (and its beam hits others).
- Fields `[0x34]`/`[0x38]` are the projectile type and strength (`weapon_shot`); the range shape is `rings.rs`, the generator `0x437b10` is `rng.rs`, flight and impact are docs/projectiles.md. Field `[0x20]` (10/20/5/1/24/16) is the shot scatter in px (volley spawner `0x47cf40`, `aim::spread`, docs/ai.md); `[0x30]` the rounds per shot.

## Advancer (kind 40) behaviour (decoded)
- Own per-tick update `0x46f210` (chassis kind `[obj+0xc]` == 0x28): frame counter `[obj+0x54]` decrements, on underflow the frame `[obj+0x40]` +1 (wraps after 31) and the counter reloads to 2, i.e. **one facing step every 3 ticks (50 ms), always, moving or not**, counting up (clockwise). The generic chassis tick skips the Advancer's frame (`0x46fe7a`). Measured on a recording: same rate and direction. It also counts idle ticks at `[obj+0x150]` and every 420 ticks calls `0x402ec0` with 0xa. OpenSOW: after 420 idle ticks of the player's Advancer (no action, no route) the message "Advancer disengaged" (`msg::ADVANCER_DISENGAGED`, `0x46f30a`), then the counter restarts at -840 (`step_actions`, `sim/advancer_actions.rs`).
- The Advancer is the only unit built with the air flag `[obj+0x4b]` (ctor `0x46bd30`, case sets `[obj+0x30]`=0x320 = 800 HP, `[obj+0x64]`=-0x17). Its sprite is drawn **64 px above** its ground point (`[obj+0x88]` = -64 for all units, only added when the flag is set) plus the hover bob `HOVER_TABLE[phase]` (-6..6, 42 phases, one step per 4 ticks = 2.8 s period; start phase random < 20); the shadow is drawn at the ground point (`0x46de10`, `0x46a310`). Table built by `0x46bc70`, verified by emulation (`opensow hover`). OpenSOW: same (spin `ADVANCER_SPIN_TICKS` in `sim/movement.rs`, hover `anim::HOVER_TABLE`, `Unit::sprite_y`). The air flag also routes the unit into the air occupancy map (`0x60ac38`/`0x62ac38` instead of `0x5eac38`/`0x61ac38`), so it ignores ground obstacles.
- Chassis draw offsets `[obj+0x2c]` (extra y, set by the chassis ctor `0x470334` from table `0x470438`): kinds 1,4,7,10,13 = -10; other ground kinds and the pod = -4; walkers 41-45 = -16; Advancer 0. The chassis draw `0x46e8f0` blits the sprite at `(x + [obj+0x28], y + [obj+0x2c])`.
- OpenSOW: the game applies them (`sim::draw_offsets`, read from the generated initialiser table: chassis `[+0x2c]` for the chassis and its shadow, top `[+0x60]` for the top, its shadow and its muzzle flash, `0x479a80` / `0x479a20`; the x offsets are 0 for every kind; `Play::draw_units`). **Differs from the exe:** the viewer's static unit preview (`opensow-viewer`, not in the exe) still draws at the ground point.

## Foreground tiles (trees, rocks) and draw order
- `Mxx.tmi` gives a tile index per cell and `Mxx.til` the 32x32 coverage mask of each tile; the set pixels are the parts of trees/rock tops that stand in front of the ground (checked on M01: the masks cover exactly the tree crowns and rock tops). The exe stamps them into the screen mask every frame (`0x459666`) and draws every ground unit (chassis, top, shadows) through that mask (`0x461da0`, `0x462110`; docs/effects.md "The screen mask"), so the background's tree tops, rock tops and tall structures such as M04's towers stay in front of every ground unit under them on screen, whatever the unit's row; the hovering Advancer is drawn unmasked over all of it. OpenSOW does the same (`Play::draw_units`). Buildings: the exe stamps each building frame's `builds\mask\{stem}.msk` frame (same index; `0x4092f0`, `0x40df80`, `0x460120`) into the same mask; its set pixels are the whole body except the front ramp of a factory, so a unit spawned inside (`0x408740`) is hidden until it walks out over the ramp. Turrets have no mask wired and use the old rule (units above the foot of the footprint are hidden: the turret is drawn again over them). Draw order (`0x41f9xx..0x420xxx`, traced): background and buildings (`0x4092f0`), ground units by y in four passes (`0x46a3a0`, `0x46a4a0`, `0x46a3f0`, `0x46a420`), the UI selection, bullet shadows (`0x410f10`), effect sprites (`0x4673a0`, `0x414730`), then the air pass: the Advancers' shadows on the ground (`0x46a370`, also over buildings), the bullets themselves (`0x410a30`, the decoded draw function), and last the Advancer bodies (`0x46a310`, at the hover height). So the beam sparks lie over buildings and tanks but under the Advancer (`draw_air_pass`; test `the_advancers_beam_sparks_are_drawn_under_its_body`).
- **Differs from the exe:** turrets hide the ground units above the foot of their footprint (`Play::finish_ground`); the exe stamps no mask for them. (An earlier version drew the tile rows after the units standing in them and redrew buildings over units; a tile row above a unit's row was then drawn under it, so units behind M04's towers showed on the domes. The exe never did that: its ground-unit draw is the masked `0x461da0`, not the plain `0x46e8f0`, which only the Advancer uses.)
- A captured building is rebuilt at 1 hp in the new colour (scaffold / construction / finished by thirds of hp while `heal > 0`). A neutral building always shows its grey frame (state 6), whatever its hit points: the state code `0x40e0df..0x40e0ee` (`cmp [b+0x8c], 2; cmove ebx, 6`) overrides the hp stages for owner 2. An earlier version added a colourless damage frame; that was not in the original and is gone.

## The Advancer's gun (top case `0x47a8af`)
The Advancer is not weaponless: its top constructor case (index kind-1 = 39 in the table `0x47ac70`) sets range 0-10 cells (`[+0x18]`, `[+0x1c]`), bullet type **31** (`[+0x34]`), strength **64** (`[+0x38]`), one step with `[+0x210]` = 4 (5 ticks), reload 180 +- 36 from the shared tail `0x47a57a`. Being a flyer (`[unit+0x4b]`), its target search in `0x46c990` is `0x47aed0` (ground grid cells whose handle type is 5 = anti-air kinds 1, 2, 3, 42; kind 110 is type 6 and building handles never match), then, if nothing was found, `0x47ad30` (air grid: enemy Advancers). So it auto-fires at enemy anti-air walkers and Advancers in range, never at other units. The search is only blocked while the chassis order type is the beam approach (`[chassis+0xe0] == 2`), so it works while flying to a building (that go-to is order type 1, `0x46b9c6`) and while hovering over it and beaming it; only a type-2 straight order (never given for building actions) blocks it. Hits subtract the strength from the unit by handle (`0x4108bc..0x4109b8`). `weapon_shot(40)`, `aim_params(40)`, `World::advancer_target`. The bullet (type 31, speed 600) has no sprite, but its flight step (`0x411b0c`) drops an additive `bodky` spark animation every 2 path steps (frames 0..1, period 1, 15 passes, call site `0x411b8a`): the constructor (`0x412240`) sets `[+0x268c] = 2*(player != 0) + 1`, so player 0 shoots a **blue** beam (`bodky_b`) and every other side a **green** one (`bodky_g`); array = `0x5e6b80 + 80 * [+0x268c]`. `effects::gun_trail`, `World::step_bullets`; exe test `the_advancer_gun_beam_matches_the_exes_flight_step_and_constructor`, game test `the_advancer_gun_draws_a_blue_beam_for_the_player_and_a_green_one_for_the_enemy`. The beam starts at the shooter's **sprite** (`0x479e0e..0x479e20`: unit position + hover offset `h` for a flying shooter, plus the top's `[top+0x40]` = `[top+0x60]` = -16, copied at `0x47abbc`) and ends at the target's sprite `(x, y + h)` for an Advancer (the facing aims at `y + h/2`), at the unit's position for an anti-air walker. The bullet's constructor (`0x412240..0x412276`) plays `tt-fire` (sfx 56) at the start point. The damage lands with the bullet (`World::shoot_at`).
