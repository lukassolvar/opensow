# Projectiles and damage

Code: `crates/opensow-formats/src/projectile.rs` (random curves: `curves.rs`); CLI `opensow weapons`; tests `weapon_shots_match_the_exes_top_constructor`,
`bullet_types_match_the_exes_constructor` (`tests/real_data.rs`).

## Pipeline
1. A top fires on the first tick of a fire-sequence step (`docs/art.md`, Fire and recoil). The spawner (`0x47cf40` -> `0x47cf70`) creates `shots` bullets, bullet *i* using `.po1` table `barrel + i`: start = `unit position - po1[table][facing]`, aim offset from `po2 - po1`.
2. Each bullet is built by `0x411dc0(type, strength, start, end, owner)` (object size `0x26cc`, 35 types, jump table `0x412490`). The type's cases set speed, a step interval and sprite animation fields; the weapon's strength goes to `[bullet+0x2660]`.
3. The bullet walks a precomputed path of points (`[bullet+0xd44..]`, count `[0x2648]`; built by `0x40ef60`, see Paths below). **Speed = path steps per 60 ticks**: the number of steps taken on each tick comes from a table built at start-up (`0x436df0`): row `v` marks `v` evenly spaced ticks of a 60-tick cycle by stepping a float by `60/v`; rows above 60 are `row(v-60)+1`. So speed 60 is one step per tick, 360 six, 1800 thirty (`projectile::steps_at`).
4. On impact (`0x4107f0`) the bullet subtracts its strength from the unit it was aimed at (turret HP `[obj+0x2c]`, unit current HP `[unit+0x34]`, which also starts a hit flash) and calls the area damage `0x42f2c0(x, y, strength, owner, type)`:
   - every **ground unit** (`[unit+0x4b] == 0`; flyers - the Advancer - are immune, `0x42f30e`; the game does the same) with `distance < 32` px loses the **full strength**, whoever owns it (no friendly-fire check);
   - kinds 109..113 are the **gun tops of finished turrets**: such a unit within 32 px does not lose hit points, its turret does (`0x42f346..0x42f38d`: `0x43a910(top's building handle)`, `[bld+0x74] -= strength`, tally += strength) - the full strength for every bullet type, no half damage, on top of the cell test below (the game: `World::explode`; test `a_blast_next_to_a_turrets_gun_top_damages_the_turret_twice`). A bomb on a turret's cell therefore does 110 + 110, and a fighter's missiles, which land 22 px beside the aim point (outside the 1x1 cell), hit through the top only;
   - bullet type 30 spares kind-45 units of the shooter's own team (the nuke walker);
   - the building in the impact cell loses damage `d` from `[bld+0x74]`, tallied per player at `[bld+0x7c+owner*4]`. `d` comes from `type - 17` through a byte table `0x42f474` into a jump table `0x42f468` (`projectile::building_hit`, `building_damage`; exe-tested): types **24, 25 (meteors) and 35 (Rogon blast) do half** (`strength / 2`, rounded toward zero) and types **17, 18, 26** (Tripler pod, bomber bomb, fighter bomb) full damage, but all six do **nothing to a Headquarters** (`[bld+0x94] == 100` is the building *kind*; the "shield" is the HQ). Every other type, including everything below 17, does full damage to any building.
   - `distance` (`0x437720`) is `trunc(sqrt(dx^2 + dy^2))`, 200 when either axis differs by more than 200.

OpenSOW: same (`World::shoot_at` spawns, `World::step_bullets` flies, `World::explode` with `projectile::splash_victims` / `building_damage` lands, `sim/combat.rs`).

Unit max HP is 180-600 for ground units (`docs/levels.md`), so one 5W5 shot (920) kills anything on the ground nearby.

## Bullet type table
`projectile::BULLET_TYPES` lists, for each of the 35 types, the speed `[+0x2664]`, the interval `[+0x264c]` (default 100; for type 1 it paces smoke puffs of the trail) and the four animation fields `[+0x2670/2674/2678/267c]`.
Types 19-21 (Advancer beam sparks) and 23 (dim effect) contain loops and a branch the generic table cannot hold; they are decoded in `sparks.rs` and checked in emulation (below). Type 32 computes its speed with the random generator (13 and 14: `curves.rs`); 28, 29 and 31 also run effect code. Those are not cross-checked against the exe; all other types are.
Types 13 and 14 are decoded: speed 30+rand(60) / 60+rand(30), see below.

**Differs from the exe:** type 2 (turret 5's shot) draws a random start delay 0..4 (`[+0x26ac]`), so each shell starts a few steps along its path; OpenSOW passes delay 0 to `build_path` for every shot (`World::shoot_at`), so `Path::first_step` is always 0.

## Paths (`projectile::build_path`, viewer `--shot x1,y1,x2,y2,type`)
- The constructor passes start `(x1, y1)`, end `(x2, y2)` and a delay (`[bullet+0x26ac]`, a random 0..4 for type 2) to `0x40ef60`; the bullet starts at the start point.
- Ground track: an integer **Bresenham line**, one pixel on the long axis per step, start excluded, end included, at most **800 points**; each point is stored as (x, y) at `[bullet+0xd44+8i]`.
- Arc types lift the bullet by `h(i)` pixels at step `i` of `N` (subtracted from y; kept at `[bullet+0xc4+4i]`, probably for the shadow): types 2 and 3 `h = i - i*i/N` (peak N/4: the tier-1 artillery shell is type 3), type 4 `h = (i - i*i/N) * 20 / 13` (peak ~0.385 N: tier-2/3 artillery), types 15 and 16 `h = 4i - 4i*i/N` (peak N). Paths that hit the 800-point cap are not lifted. All other types are straight.
- Types 13 and 14 copy one of 200 random curves, see Random-curve bullets below (`curves.rs`; `build_path` still returns `None` for them).
- The start index is `delay` (steps skipped) unless the path is not longer than it.
- Flight time: `flight_ticks(speed, steps)`; e.g. a 400 px cannon shot (type 6, speed 1800) takes 14 ticks, a 400 px type-4 shell (speed 120) about 200.

## Random-curve bullets (types 13 and 14, `curves.rs`)
(Checked against the exe 2026-11-06: the building draw `0x4092f0` has no dead state, the sounds 24/25 are gated by `[b+0x2c8] == 0`, which is 1 only for the menu/preview copies, so the burst matches.) Debris of a destroyed building: the destruction animation (`0x409b60`; every time its counter `[b+0x110]` runs out it throws 3 bullets of type 14 and 3 of type 13, strength 80, owner = the building's, then sets the counter to 90 + rand(15)). Not used by any weapon. The first burst comes on the very first pass (`[b+0x110]` starts at 1). **Animation length** (corrected 2026-11-06; an earlier note took `[b+0x108]` for a step count): every pass counts `[b+0x110]` down, and only when it reaches 0 is the animation counter `[b+0x10c]` (= `[b+0x108]`: 5 for buildings, 2 for turrets, `effects::destruction_bursts`) decremented; if it is then still above 0 the burst is thrown and `[b+0x110]` is reset to 90 + lockstep `rand(15)` (a draw after the six bullets), otherwise the animation ends. So a building bursts four times and ends on the fifth round (about 360 passes), a turret bursts once and ends on the second (about 90 passes); `0x409b60` runs 2 passes per tick, so about 3 s and 0.75 s. The building stays on the map, dead (hp <= 0, state 2), until the end; only then the stats count, the capture or removal `0x43ab40` runs and the win/lose scan `0x4212f0` (which only looks for kind 100 in the object table) stops seeing an HQ. Ported as `World::destruction_pass` / `step_destruction`; `building_destruction_animation_lengths_match_the_exes_constructor` checks the constants: lockstep `rand(15)`, `rand(w*32-20)`, `rand(h*32-20)` pick a point in the footprint (10 px margin); area damage there (turrets 50; others 80 when the first draw is 5 or less, else 50), an `e_turret` / `e_bubg` blast, sound 25 (and sound 24 when the visual `rand(7)` is 2), then the six bullets from that point (`0x409b60`, `0x409d86..0x409e67`).
- **Curve table** (`0x40f2c0`, called from game init `0x422c13` straight after the lockstep RNG index is set to 0, so the table is the same in every game; the 600 draws leave the index at 600): per curve k < 200, `dx = rand(300)-150`, `dy = rand(300)-150`, Bresenham line from (0,0) to (dx,dy) as in the normal path builder (start excluded, `max(|dx|,|dy|)` points, n), then `rand(3)`: 0 -> lift `h(i) = i - i*i/n`, else `h(i) = 2i - 2*i*i/n`; `y -= h(i)`, lift kept per point. Stored at `0x4ec098` (counts, 2 per point), `0x49de98` (points, `0x640` bytes per curve) and `0x4ec228` (lifts, `0x320` per curve).
- **Constructor** (`0x411dc0`): type 13 `[+0x265c]=1`, `[+0x268c] = rand(2)`, speed `30 + rand(60)`, anim fields `[0,16,1,2]`; type 14 `[+0x264c]=3`, speed `60 + rand(30)`. **Path** (`0x40ef60`, via `0x40ef10`): `rand(200)` picks the curve, points are the curve plus the start (the end point given is ignored); first step `delay*2` (0 here). Draw order per bullet: constructor numbers, then the curve number (`curves::RandomBullet::draw`).
- **Flight** (`0x411220`): the common step loop; type 13 (not 14) also copies the lift to `[+0xc0]` each step (shadow). After the last point the bullet is removed, and the removal (`0x40f590`) has no special case for 13/14, so it does the generic area damage `0x42f2c0(x, y, 80, owner, type)` at the last point (checked in emulation: it is called for 13 and 14).
- Verified by `scripts/verify_against_exe.py` section 1b: the whole table (counts, points, lifts, RNG index 600) and 300 constructor+path draws are identical to `opensow curves|curvebullet`. Wired into the game: `World::destruction_burst` (the curve table is built in `set_game_rng`, which leaves the random table at index 600 like a new game in the exe).

## Beam sparks and dim effect (types 19-21, 23; `sparks.rs`)
Constructor cases `0x412408` (19), `0x4123aa` (20), `0x412333` (21), `0x411ee0` (23). Each fills three int arrays in the bullet: `A[i]` at `[+0x0c+4i]` (x offset), `B[i]` at `[+0x48+4i]` (y offset), `C[i]` at `[+0x84+4i]` (frame), `i < [+0x268c]`. The randomness is `0x437cd0`, the *visual* generator (C `rand()` table, not the lockstep one), so the values are not reproducible, only their ranges:
| type | action | speed | `[+0x264c]` | fragments | `A` | `B` | `C` |
|---|---|---|---|---|---|---|---|
| 19 | repair (`bodky_b`) | 60 | 100 | 5 | `rand(30)-15` | `rand(20)-10` | `rand(3)` |
| 20 | upgrade (`bodky_y`) | 60 | 2 | 2 | `rand(20)-10` | `rand(20)-10` | 0 |
| 21 | destroy (`bodky_r`) | 60 | 100 | 12 | 0 | `-i` | `rand(2)`, then fragments 9, 10, 11 forced to 0, 4, 0 |
Draw order per fragment: x, y, frame. Type 21 also sets the start delay `[+0x26ac]` to 5 (the `-i` comes from reusing the owner argument slot `[ebp+0x20]` as a down counter after it was copied to `[+0x266c]`). Type 23 (`dim1..dim4`, 21 frames each): speed 60, counter 0, period 1 / 3, and the end frame `[+0x2674]` is 16 for variant `[+0x2680]` 0 or 2, otherwise 20. Checked against the exe by `scripts/verify_against_exe.py` (visual RNG hooked, 400 constructor runs); `opensow sparks`. OpenSOW: `advancer::fragment` per fragment, drawn by `play.rs` (`World::beams`).

**Differs from the exe:** the game draws the fragment values from the lockstep generator (`World::random`, `sim/advancer_actions.rs`) instead of the visual one, and the destroy beam (21) starts at path step 0 instead of 5.

## Targeted bullets and the handle `[+0x2688]`
The shot spawner (`0x47cf40` -> `0x47cf70`, callers: weapon tops `0x479e35`, the Advancer beam `0x46f440`) passes the shooter's **target handle** (`[top+0x7c]`) as its fifth argument and stores it at `[bullet+0x2688]` (`0x47d0fe`; the satellite check `0x40a0b7` stores the Advancer's `[unit+0x3c]`). A handle is a 32-bit number: slot index in bits 0..9, player (side) bits 16..18 (`0x43aa80`), class bits 19..21 (`0x43aaa0`: 4 = a unit on the air grid), subclass bits 22..24 (`0x43aab0`: 4 = aircraft, 1 = ground unit, `0x43aac0` checks it); 0 = none. Only bullet types **1** (anti-air missile), **10** (satellite laser) and **31** (the Advancer's gun) use it: the impact function `0x40f590` sends them to `0x4108bc` instead of the generic tail. There, subclass 4 loops over the side's aircraft array `0x5ba910` (30 per side) and subtracts the strength from `[aircraft+0x2c]` of the entry whose `[+0x1c]` equals the handle; any other handle loops over the three sides' unit arrays `0x5b62c0` (1000 slots each) for the unit whose `[+0x3c]` matches, subtracting from `[unit+0x34]` and setting the hit flash `[+0x5c] = 180`, `[+0x60] = 5`. **No area damage, no splash on neighbours, and nothing at all when the target is gone** (died or was removed meanwhile). The damage comes when the bullet lands, not when it is fired. `World::shoot_at` / `hit_target` implement this for the three shooters (anti-air units, the anti-air turret, the Advancer gun); aircraft carry an `id` in place of the exe's handle. Exe-tested by `targeted_bullets_hit_their_handle_in_the_exes_impact_function`. (An earlier version of the sim took the strength off the target at the moment of firing.)

## Range rings
- `0x436230` builds, at start-up, a list of cell offsets `(dx, dy)` (words at `0x65bbd8`) and a cumulative index table (dwords at `0x6b3a18`, value = words up to and including ring `r`; `T[0]=2` is the centre). `rings::Rings::generate()` reproduces both exactly (`opensow rings`).
- Target search (`0x47b140`, args: x, y in pixels, ..., `min` at +0x18, `max` at +0x1c) shifts the position to cells (/32) and scans offsets from `T[min]` to `T[max]`, so a range covers rings `min+1 ..= max`. `max == 1` uses the 8-neighbour list at `0x6b3c70` instead (`rings::NEIGHBOURS`, copied from `0x48ef20` at `0x436250`), read from word `T[min]` up to word 16 (`0x47b18d..0x47b1ad`): with `min = 0` the first entry `(-1, 0)` is skipped, so a range-1 weapon (walker 45) scans 7 cells and never the one to its west; `min = 1` would scan the last three diagonals. OpenSOW: `Rings::target_search` (target search and both range overlays); test `range_one_scans_seven_neighbours_without_the_west_cell`. The port used ring 1 (4 orthogonal cells), so walker 45 stopping on a diagonal next to turret 1 never fired. Cells outside the map are skipped.
- Shape: ring `r` holds the cells an octagon of size `r` newly reaches. It is NOT a pure distance band: the farthest cell of ring `r` is `r^2 + floor((r-1)/2)^2`, but cumulative sets are exact discs only for r <= 7 and r = 9 (e.g. (6,6), d2 72, is in ring 9 while (8,3), d2 73, is in ring 8). Point counts for r = 0..9: 1, 4, 8, 24, 20, 40, 32, 56, 44, 72.
- Generator: 16 corner counters of a closed octagon, 145 steps cycling state 2, 3, 4 (2 and 3 close a ring and record the index, 4 only grows the octagon, so its new cells join the next ring). Each step walks the 8 edges (diagonal, horizontal, diagonal, vertical, ... ) emitting unvisited cells on a 300x300 grid; the centre is never marked visited. Order inside a ring is the edge walk order, which the search relies on to pick the first hit.
- OpenSOW: same list (`rings::Rings`), used by the game's target search (`sim.rs`).
- Viewer: `--range CX,CY,MIN,MAX` (repeatable) shades rings `MIN+1..=MAX` around a cell, alternating tints per ring.
- The `0x47d7fb/801/807` calls inside it only update 30 UI helper objects (`0x70f030`) and do not affect the list.

## Verification against the exe
`scripts/verify_against_exe.py` runs the exe's own functions in an x86 emulator (unicorn) and compares them with the Rust ports on random inputs: bullet paths (`0x40ef60`, 1500 cases over 22 bullet types), the speed table (`0x436df0`, every row), heading -> facing (`0x46b180`, 2500 cases incl. 32/16/8 steps and degenerate points) the turn step (`0x46a190`, 1500 cases) and the ring list builder (`0x436230`, whole index table + 14017 offsets). All match (0 mismatches). The run found three bugs in earlier hand-reading: paths at the 800-point cap are not lifted, the 8-step facing mode is live (`(2 - round(theta/45)) mod 8`, default 2), and none in the speed table or turn step.

## Not decoded
The sprite of each bullet type and the blasts are decoded (docs/effects.md). The network serialisation (`0x4128f0`, reader `0x412620`) is decoded in docs/network.md (`netsync::BulletSync`); `0x412620` is the record reader, called from `0x421f60`.

## Method notes
- Weapon constructor cases share tail code, so extraction must follow the unconditional jumps up to `0x47ab5f`/`0x47ab66`. An earlier cut-off version gave several kinds reload 0 (corrected in `aim.rs`: kinds 2, 3, 11, 12, 14, 15, 42, 45).
- The test decoders in `tests/real_data.rs` (`Exe::top_case`, `Exe::bullet_case`) follow jumps and fail loudly on unknown opcodes.
