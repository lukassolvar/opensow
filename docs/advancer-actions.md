# Advancer actions: destroy / capture, repair, upgrade (decoded)

Code: `crates/opensow-formats/src/advancer.rs`, sim in `crates/opensow-game/src/sim.rs` (`order_action`, `step_actions`, `structure_destroyed`). Exe test: `building_hit_points_match_the_exes_constructor`.

## Rules (manual + tutorial strings)
- Select the Advancer and click a building. Enemy/neutral buildings are attacked and, when their hit points run out, **captured**; own buildings are **upgraded** (green arrow) or **repaired** (RMB toggles the mode). Turrets: own ones are repaired, enemy ones destroyed. "Advancer disengaged" = idle Advancer.
- Satellite protection: every HQ (`[b+0x114] = 1`, ctor `0x40a47a` for kind 100) and objects with word 15 set; the destroy beam sets `[b+0x118]`, and the per-tick check `0x409f50` (timer `[b+0x11c]`, 240 ticks) kills foreign Advancers above the footprint with the satellite laser (docs/effects.md). In the game (`step_satellites`). **Label:** the health-bar draw `0x409400` (selected branch `0x40952c`, hover branch `0x4095d9`) adds the string index 145 "SATELLITE PROTECTION" for buildings with `[b+0x114] != 0`: GDI text (`0x467060`, white, black shadow +2,+2, font `[0x5ddf20]` = `CreateFontA(11, 0, ..., 700, "Times New Roman")`), left edge 46 px left of the footprint's middle, top 6 px above the bar's first row (`[b+0x120] - 6`) when the building is selected, 10 px when it is only hovered. `Play::draw` (the game stands in with the system Times New Roman Bold at 11 px via `gdi.rs`, drawn 5 px higher than the exe so it does not hide the bar; bitmap fallback).

## The pointer (decoded, docs/cursor.md)
With an Advancer selected the pointer over a building shows the order a click gives: red arrow (7) destroy for enemy and neutral buildings, purple wrench (6) repair for damaged own buildings, green arrow (8) upgrade when an own building has a locked slot, plain go-to (3) otherwise and for the own HQ. `advancer::pointer_over_building`; `World::action_for` uses it, so click and pointer cannot disagree. A right click on an own building toggles repair-first mode.

## The order (decoded)
- Network commands `CNet_HDestroy / HRepair / HUpgrade` (arrays `0x49a484 / 0x49a498 / 0x49a4ac`) come from the Advancer methods `0x46b8b0` (destroy), `0x46b9f0` (repair), `0x46bb30` (upgrade). Offline they call the top's setters `0x46e5c0 / 0x46e620 / 0x46e680`: `[top+0xf4/+0xf8]` = target cell centre px, `[top+0x100]` = target building id, `[top+0xfc]` = mode 1/2/3, `[top+0x130]` = event code 0x15 / 0x13 / 0x14. Then the normal goto (`0x4706a0`, order type 1 - not the straight type 2) flies there, with avoidance: only one Advancer can hover over the work cell, a second one ends next to it and cannot shoot.
- The Advancer update (`0x46f210`) cancels the mode if its move goal leaves the target cell. When it sits on the target cell (`[+0x5c/+0x60]` == goal == target), the mode is set and the beam object (`[top+0x104]`, state `[top+0x144]` == 0 means idle) is ready, it re-checks the target (`0x46f3a6`): the building must still exist; **repair** needs `hp < max_hp` (`[b+0x74] < [b+0x70]`), **upgrade** needs `[b+0x144] < [b+0x140]` (active < available slots); then it spawns the beam/event with `0x47cf40` and sets the beam state to 6. Sound plays every third shot.
- Beam shots are events (object size 0x26cc, init `0x411dc0`, code `[+0x2658]`, target building id `[+0x2688]`, player `[+0x266c]`) run once by `0x43a6d0` -> `0x40f590`.

## Effects of one event (`0x40f590`, per beam shot)
- Strength `rate = [0x5baaac + player*4]` = **level header word 31 (player 0) / 32 (player 1), used as is** for every shipped mission and map (`0x41d7a3..0x41d7cd`: the level id, header word 1, is read just before the header block; only id 0 shifts the words left by 2). The words are 6..15, usually 10 (M01: 12 / 8). An earlier version multiplied by 4, making upgrades and repairs four times too fast.
- **Destroy (0x15):** `hp -= 2*rate`, `tally[player] += 2*rate`, flag `[b+0x118] = 1`. **Repair (0x13):** `hp += 2*rate`, `tally[player] -= 2*rate` (not below 0); at full hp the Advancer's order is cleared (message "Turret/Building repaired"). **Upgrade (0x14):** `0x40e3d0`: `[b+0x148] += rate`; when it reaches the target of slot `n = [b+0x144]` (2000 ground / 4000 air) the active slot count goes up by one (sound 4) and the points reset.
- Normal bullet damage to buildings does the same bookkeeping (`0x42f2c0`): `hp -= dmg`, `[b+0x7c + attacker*4] += dmg`. So `tally[p]` (0 blue, 1 green, 2 neutral) = damage dealt by player p.

## Capture
- A building's constructor (`0x40a330`) sets max hp `[b+0x70]` by kind (jump table `0x40afb8`): **turrets 900 / 1250 / 1540 / 2100 / 2600 (kinds 25-29), every building 100-108 = 13536**, 109-113 and other = 50. It starts at **hp 1 with a pending heal `[b+0x6c]` = max** that the building update (`0x40de60`) pays out at **150 hp per tick**.
- hp <= 0 (`0x40de60` -> `0x409130`): flag `[b+0x69] = 1`, destruction state `[b+0x104] = 2`, explosion sounds (turret 0x57 / building 0x1e effect), then `0x409b60` runs the destruction animation. When it ends, the player loop `0x42dc60` calls `0x43ab40(player, index, 0)`: turrets (0x19-0x1d) and the HQ (0x64) are removed (`0x43a640`), **every other building is rebuilt for the player with the largest damage tally among those who are not the current owner** (`capture_winner`; nobody -> **player 1** in single player, `0x43ac2f..0x43ac38`: `[0x575720] == 0` gives `edi = 1`; with remote players a lockstep random number). The rebuilt building keeps its kind and active-slot count, and plays sound 1. So "capturing" = destroying; the destroyer with the most damage gets it, also when ordinary bullets did it. The destroy animation length (`[b+0x108]` = 5 steps) is not applied in the game.
- The ownership message (`0x40a160`, 5 bit-fields: kind 7, id 0x20, x 8, y 8, owner 2) is the network form of the same change.

## The beam period (decoded, exact)
- The Advancer's top embeds a cooldown member at `[top+0x104]` (constructor `0x47c630`, called from the top's constructor `0x470048`): `+4` enabled, `+0x1c` counter, `+0x20` reload = **10**, `+0x24` spread = **0**, `+0x40` state. The top constructor also stores 10 in `[top+0x124]` (= member `+0x20`). Nothing in the Advancer code (0x46xxxx-0x47xxxx) writes `+0x20`/`+0x24` again, and the value does not read the level header, the action (repair / upgrade / destroy), the owner or the unit's state: **the period is the same 10 ticks for all three actions, both players and every level**.
- Per tick `0x46f210` first calls the tick `0x47c6b0` (`BeamTimer::tick`: counter above `2*reload` -> `reload`; state 6 counts down and returns to state 0 at 0 in the same tick; state 5 counts down to 0; other states idle). Only then does it test the shot conditions (`0x46f326..0x46f371`: unit pixel == goal == target pixel, mode set, `[top+0x108]` set, **state 0**, target still valid) and fires: `0x47c5f0` sets counter = `reload - spread/2 + random(spread)` - with spread 0 `random(0)` returns 0 without touching the generator (`0x437b10`), so no random numbers are used - and state 2, immediately followed by the state store 6 (`0x46f454`).
- So shots happen at ticks T, T+10, T+20, ... The counter runs even while the Advancer is flying away or has no order, so a new order given less than 10 ticks after a shot waits for the rest of the reload (the old sim restarted the cooldown at 0). `advancer::BeamTimer`, `BEAM_PERIOD`; checked against the emulated `0x47c6b0` by `scripts/verify_against_exe.py` (`opensow beamtick`) and the exe test `advancer_beam_period_comes_from_the_exes_cooldown_member`.

## Where it hovers, the shot, the effects (decoded)
- **Art anchor**: the building sprite is drawn with its hotspot at `cell*32 + (b+0x1c, b+0x20)` (`buildings::art_offset`: e.g. lab (48, 39), HQ (64, 48), 1x1 turrets (16, 20..22)); the viewer used to anchor at the cell centre, which put every building one cell left of where the Advancer hovers.
- **Cell**: `0x46b8b0` sends the Advancer to pixel `(x*32+16, y*32+16)` with `x = [b+4] + width/2` (`0x409ab0`) and `y = [b+8] + r` (`0x409ac0`): `r` = the first blocked row of the layout in the middle column `width/2`, else `height/2`; kinds 28, 29, 108 use row 1. `buildings::advancer_offset`, `Structure::action_cell`. The shot needs the unit's pixel position to equal that pixel exactly (`0x46f326..`).
- **Shot** (`0x46f3fb..0x46f440` -> `0x47cf40` -> bullet ctor `0x411dc0`): one bullet of **type = action code** (19 repair, 20 upgrade, 21 destroy; constructor cases `0x412408`, `0x4123aa`, `0x412333`) from the hovering unit (`x`, `y + hover`) to the target pixel, **speed 60 = one path step per tick** (so ~64-70 ticks of flight straight down), id of the target building in `[bullet+0x2688]`. The action itself happens when the bullet **lands** (impact function `0x40f590`; buildings are looked up by id, so a building that changed hands meanwhile is not hit). **Beam period = exactly 10 ticks** (6 shots/s), see below. Every third shot (first, 4th, 7th...) plays the sound `0x4111b0` (counter `[top+0x15c]`, reset to 3).
- **Sprites** (`extras\bodky_*`, additive): repair = 5 blue sparks (`bodky_b` frame `rand(3)`, offsets `rand(30)-15`, `rand(20)-10`) flying together; destroy = a column of 12 red sparks (`bodky_r` frame `rand(2)`, offsets `(0, -i)`); upgrade = the bullet itself is invisible but every 2nd step drops 2 yellow sparks (`bodky_y` frame 0, 11 ticks each, offsets `rand(20)-10`, `0x411993..0x411a1e`). On landing: repair 5 `bodky_b` frames 6..9 (period 4) at the fragment offsets (`0x410063`), destroy one `bodky_r` frames 6..16 (period 2) at the landing point (`0x410342`), upgrade nothing.
- **Draw order** (`0x41fc.. 0x420400`): animation sprites (`0x49a398` list: the yellow trail sparks, blast and the click marker), then bullets, then the units - the Advancer covers the sparks near its body, they come out from below it. `Play::draw_shots` before `draw_units`.
- **Target flash** (`0x4086a0`, called when the local player orders units onto a building): `[b+0x14c]=1`, timer 5, `[+0x154]=1`, count 8; `0x40de8a..0x40dec5` toggles the state every 5 ticks eight times; `0x409467` draws the building's own sprite again half-additive (`0x45c220`) while on. `World::blink`, `Blink`, `Play::draw` (before the shots). Also on attack orders onto buildings.
- **Health bars**: buildings only while selected or hovered (`0x409400`: `[b+0x88+player]` selected -> `0x437140`, hovered -> `0x436f40`); bar width `max / scale` px (scale 144 for buildings, 72 for turrets, `0x40a981..0x40aa01`), centred on the footprint at its top edge (`[b+0x120] = cell.y*32`), fill by `hp / scale`, colour by ratio (> 1/2 green, > 1/4 yellow, else red). Unit bars use the same routine: the unit's selection pass `0x46a420` calls `0x437140(max_hp [+0x30], hp [+0x34], scale [+0x38], x [+0x14], y [+0x18] + [+0x64] (+ hover for the Advancer), ...)` for every unit selected by the local player (`[0x575730 + unit + 0x48]`): centred, 25 px above the ground point (23 for the Advancer, `[+0x64]` -25 / -23), `max_hp / 16` px wide (`/ 20` for the Advancer). **Drawing** (`0x437140`, RGB565): a 1 px frame `0x0001` around `max/scale` x 3 px; filled part `hp/scale` px in three rows, empty part `0x0066`; green rows `d7f3 64a8 3323` while hp > max/2, yellow `ff94 b583 7b60` above max/4, red `fd32 c221 8060` below. The game's `health_bar` (play.rs) draws buildings, turrets and units with it, every exe pixel scaled by the zoom. The exe draws **no selection frame** around selected units (`0x46eb40` is the order marker), so none is drawn.
- **No world progress bars**: the original shows upgrade progress only in the selected building's slot column (green bar of the slot being unlocked).

## In the game
`World::order_action` (left click on a building with an Advancer selected; `R` or a right click on an own building toggles repair vs upgrade), `step_actions` ticks each Advancer's `BeamTimer` every tick and fires when it is idle (`ADVANCER_BEAM_TICKS` = 10 ticks), `step_beams` flies the `BeamShot`s and `beam_lands` applies them; `Play::draw_bullets` draws the sparks. Only factories can be upgraded (other buildings have no slot effects yet). Headless: `--play M01 --act 13,38 --ticks 3400 --report` (the Advancer needs ~3000 ticks to fly there).

## Satellite check `0x409f50` (decoded, exe-tested by `satellite_check_scans_the_footprint_on_the_air_grid`)
- Caller: only the tail of the building update (`0x40e383..0x40e38e`), for buildings with `[b+0x114] != 0` (every HQ, ctor `0x40a47a`; other buildings get the word from the level object, `0x41dffc`, word 15). `[b+0x118]` = "attacked" flag, `[b+0x11c]` = cooldown; both are zeroed by the constructor and saved (`saveobj.rs`).
- The flag is set **only** by the Advancer's destroy beam landing (`0x4102f7`, in `0x40f590`); ordinary bullet damage (`0x42f2c0`) never touches it, so only Advancers trigger the satellite.
- Per call: gate `0x41f020([0x575730])` returns true only with remote players (`[0x575720] > 0`) and a non-zero argument, then the whole check is skipped (flag and timer untouched); single player always runs it. Then `cooldown -= [0x552494]` (ticks of the frame) while > 0. If flag == 1 and cooldown <= 0: cooldown = **240**, and every cell of the **bounding box** `[b+4..b+4+[b+0x14]) x [b+8..b+8+[b+0x18])` is looked up on the **air grid** `0x60ac38` (index `x*128 + y`): a handle of class 4 whose side differs from the building's owner `[b+0x8c]` and whose unit has kind `[+0x40] == 0x28` (Advancer) gets `hp = 0` and a type-10 bullet (docs/effects.md). With flag == 1 and cooldown > 0 nothing happens. **The flag is cleared on every call that passed the gate**, so a beam shot during the cooldown is forgotten; the first shot after it expires strikes at the next update.
- The sim's `step_satellites` matches this (the unit's cell instead of the air-grid handle; the footprint box is `footprint()`). Neutral protected buildings (owner 2) kill both sides' Advancers.

## The AI and the economy
The AI's Advancer use (`0x42fae0`) is decoded in docs/ai.md (rule 5: foreign satellite-protected buildings score -10000, so it never attacks them). The strength `rate` is not multiplied by 4 (see "Effects of one event"). The economy effects of gold mine, research lab and windtrap levels are in docs/ai.md (once per second `active + 1` credits / research points; windtrap `30 + 12 * levels` production steps/s).

- Bullet damage to buildings (`0x42f2c0` tail, `0x42f3cc..0x42f462`) has **no owner check**: the building in the impact cell (`0x43a910` on the grid `0x6f3a4c`) loses the strength and `[b+0x7c + owner*4]` gains it, whoever owns the building; nor does it look at `[b+0x68]`/`[b+0x69]`. So the exe has friendly fire on buildings. OpenSOW follows this: shells of the captor still in flight can destroy the 1-hp rebuild, which then goes to player 1 (test `friendly_shots_hit_buildings_as_in_the_exe`).
